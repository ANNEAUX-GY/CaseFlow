## 2026-10-30

本版本新增 2 个字段，没有任何删除或修改，也不改动任何已有数据。

审批表 case_approval（案件状态变更审批）
  + flow_action  阶段流转动作：DETAIN 刑拘 / BAIL 取保 / ARREST 逮捕 / RELEASE 释放 / CLOSE 解除收案
  + from_stage   申请时的案件阶段（审批时对比，防止期间被改过导致串档）

背景：新增「变更案件状态」功能——刑事初查案件对全部嫌疑人抓捕刑拘 / 取保候审后，
承办人可申请把案件流转到「刑拘在办」/「取保监居」，案管或领导审批通过才落地
（案管/领导也可直接操作）。承办人的申请内容落在这两列，审批人才能看到
「从哪个阶段、转到哪个阶段」。

另外新增「案管 CASE_MANAGER」角色（权限与法制员同级，可审批结案 / 状态变更），
这是账号表 role 字段的取值扩展，不涉及建表 / 加列。

对老数据的影响：无。两列全部允许为空，老审批行不受影响；新角色只是取值扩展。

## 2026-10-29（续）

案件编号不再自动生成，改为「导入识别到编号 / 手工输入编号才填，否则留空」。

案件表 case_info
  case_no  原为 NOT NULL（系统自动生成编号 CA-xxx / 日期-流水），
           现放宽为可空（MODIFY COLUMN ... NULL）：
           - 手动建案：case_no 留空，业务编号走 filing_no（案件编号/受案号）；
           - Excel 导入：识别到「案件编号」列就存该值，没识别到就留空；
           - 不再自动生成编号（原来 generateCaseNo 保证每案必有编号）。
           这是「放宽」约束：不删列、不改类型、不动已有值——老案件的编号仍在，
           只是允许以后新增的案件编号为空。UNIQUE 约束保留（MySQL/H2 都允许多个 NULL）。
           程序启动时由 SchemaMigration.relaxCaseNoNullable 幂等执行；
           DBA 若单独执行，等价 SQL 为：
             ALTER TABLE case_info MODIFY COLUMN case_no VARCHAR(64) NULL;

对老数据的影响：无。老案件已有编号不受影响，只是允许新案件编号为空。

## 2026-10-29

本版本新增 1 张表（工作记录本），没有任何删除或修改，也不改动任何已有数据。

新表 work_log（工作记录本）
  民警个人工作记事本。记录每个民警具体做了什么工作：
  - employee_id / employee_name  记录归属的民警（挂在员工档案上，账号停用不影响归属）
  - content                      工作内容
  - case_id / case_name          可选的关联案件（纯个人记事可不挂案件）
  - creator_id                   记录人账号
  - created_at / updated_at      记录时间 / 最后修改时间
  权限：普通民警只看/只写自己名下的记录；其余角色（所长/副所长/队长/法制员/
  研判员/系统管理员）可检索查看任意民警的记录。

对老数据的影响：无。这是一张全新表，老库里没有它，首次启动由建表语句自动补建；
已有案件、嫌疑人、待办、意见等数据一个字节都不动。

角色方面（非库结构）：新增「队长」（权限同副所长）与「研判员」（查看全量案件 +
录入嫌疑人身份信息）两个角色，均为账号表 role 字段的取值扩展，不涉及建表/加列。

## 2026-10-25

本版本（相对 10-16 版本）新增 11 个字段 + 1 张内部表，没有任何删除或修改。

案件表 case_info
  + case_time          案件时间。列表"报案/受案时间"列与排序都用它；
                       老案件首次启动时由程序按受案时间（没有则创建时间）自动回填。

嫌疑人表 case_suspect
  + measure            当前强制措施：拘留 / 逮捕 / 取保候审 / 监视居住 / 拘传
  + measure_start_at   本次措施的开始时间
  + measure_end_at     本次措施的结束时间（下一节点），用于到期提醒

审批表 case_approval（强制措施变更审批）
  + apply_measure      申请变更成的措施
  + apply_date         申请的起算日
  + apply_deadline     申请的期限届满日
  + from_measure       申请前的措施（审批时对比用）
  + applicant_id       申请人
  + applicant_name     申请人姓名
  + applied_at         申请时间

新表 schema_migration_mark
  内部台账表，只记录"哪些一次性数据整理已经执行过"，与案件数据无关。
  作用是保证数据整理每个库只跑一次，不会在后续升级中反复改动已录入的数据。

对老数据的影响：无。11 个字段全部允许为空，老数据行不需要任何转换；
老案件的 case_time 首次启动时按受案时间补齐，其他字段保持为空（界面显示"—"）。
