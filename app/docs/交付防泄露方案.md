# 交付他人电脑时的防泄露方案

> 适用场景：把 CaseFlow 部署到客户/其他单位的电脑上**正常使用**（不是演示），
> 同时不希望对方拿到可直接维护的源代码。
>
> 编写日期：2026-10-13　　适用范围：`app/backend`（Spring Boot 2.7 + JDK8）

---

## 0. 结论先行

**没有任何工具能让 jar 里的字节码变得不可反编译。**只要交付 jar，
对方装个 CFR 或 JD-GUI，几分钟内就能拿到接近原始的源码。这是 Java 生态的客观现实，
不要指望有某个开关能一劳永逸解决。

所以正确做法不是追求"绝对不泄露"，而是**分层设防，让泄露的代价变高、痕迹可追溯**：

| 层次 | 做什么 | 成本 | 拦住谁 |
|---|---|---|---|
| 第一层 | 交付物瘦身：只发成品，不发源码 | 极低（1 小时） | 99% 的情况 |
| 第二层 | 代码混淆 + 配置外置 | 低（半天） | 有一定技术能力的人 |
| 第三层 | 授权绑定 + 防复制 | 中（1–2 天） | 商业级防复制 |

**优先级：第一层必须做，第二层建议做，第三层按商业需要决定。**

如果只做一件事，就把第一层做扎实——**别发源码、别发开发环境、别发演示数据**，
这一层的性价比远高于后面两层。

## 1. 当前交付物的实际泄露面

以下是 2026-10-13 对 `app/backend/target/case-flow-backend.jar`（73 MB）的实测结果。

### 1.1 高危：Java 字节码

```
BOOT-INF/classes/com/caseflow/**/*.class    共 134 个 .java 对应的字节码
```

用反编译工具打开后，`FlowService`（办案阶段流转）、`CaseSnapshot`（快照与撤回）、
`StaffTodoService`（待办派生）这些核心逻辑基本可读。**这等同于交源码。**

### 1.2 中危：配置文件

| 文件 | 问题 |
|---|---|
| `BOOT-INF/classes/application-mysql.yml` | 默认账号口令 `caseflow/caseflow` 明文写死 |
| `BOOT-INF/classes/application-dev.yml` | `spring.h2.console.enabled: true`，一旦被启用可绕过登录直连数据库 |
| `BOOT-INF/classes/application.yml` | 默认 profile 是 `dev`（H2），正式环境需显式改 |

### 1.3 中危：建表脚本

`BOOT-INF/classes/sql/schema.sql` 与 `index-mysql.sql` 明文在 jar 里，
18 张表的字段、索引、外键一览无余。表结构本身不算核心机密，但没必要主动送。

### 1.4 低危：前端

前端产物已 minify、`dist` 内**无 sourcemap**，这部分泄露极少，无需处理。

### 1.5 特别提醒：源码包

`release/caseflow-source-1.0.0.zip`（5.9 MB）**含全部 Java/Vue 源码**。
它就躺在 release 目录里，交付时极易误发。**交付前务必确认这个 zip 没有被带出去。**

## 2. 第一层：交付物瘦身（必做）

思路：**对方电脑上有且只有运行所需的东西，没有一样是能用来二次开发的。**

### 2.1 交付清单

部署目录应该长这样（只有 4 项）：

```
CaseFlow/
├─ case-flow-backend.jar      唯一的服务程序
├─ runtime/                   便携 JRE 8（200 MB，免装 Java）
├─ config/                    外置配置（口令在这里，不在 jar 里）
│   └─ application-prod.yml
├─ data/                      数据库文件 / 附件（首次启动自动生成）
├─ logs/                      日志
└─ 启动.bat                   双击就能跑
```

**不应该出现的东西**（出现即泄露）：

- ❌ `app/`、`src/`、`frontend/`、`node_modules/`
- ❌ `pom.xml`、`package.json`、`*.py`（构建/自检脚本）
- ❌ `tools/`（JDK/Maven/Node 整套工具链 500 MB+，暴露技术栈细节）
- ❌ `caseflow.mv.db`（**演示数据库含真实测试数据**）
- ❌ 任何 `*-source-*.zip`

### 2.2 落地做法（已完成）

**已实现**：新增 `scripts/package_deploy.py`，一条命令产出「全新电脑解压即用」的交付包：

```bash
.venv\Scripts\python.exe scripts\package_deploy.py
```

脚本做了这些事：

1. **干净构建**：先删 `backend/target` 与 `frontend/dist` 再构建（见 2.5 节，不 clean 会泄露旧代码）
2. **重写 jar**，剔除 `application-dev.yml`（H2 控制台）与 `sql/*.sql`（建表脚本明文）
3. 组装交付目录：jar + 便携 JRE + `config/` + 启动器 + `部署说明.md` + `使用教程/`（含 19 张截图）
4. 出包后**自动删除 `release/` 下的 `*-source-*.zip`**，从源头断掉误发可能
5. **两层自检**：校验 jar 内敏感项 + 遍历交付目录，
   发现 `.java/.vue/.py/pom.xml/node_modules/.db/-source-*.zip` 任一项即报错终止

常用参数：`--skip-build`（复用已有 jar）、`--no-jre`（目标机自备 Java）、
`--port/--db/--db-user`（预填数据库连接）、`--keep-stage`（保留组装目录便于检查）。

### 2.5 必须 clean 构建（重要）

**不 clean 直接打包会泄露历史代码。**2026-10-13 实测：

| | 不 clean | clean 后 |
|---|---|---|
| `target/classes/static/assets/*.js` | **672 个** | 29 个 |
| static 目录体积 | 55 MB | 2.5 MB |
| jar 体积 | 73.4 MB | **53.5 MB** |

其中 **643 个是 `frontend/dist` 里早已不存在的历史残留**——每次 vite build 换 hash，
旧的留在 `target/classes/static` 里没被清掉。这些旧 chunk 里包含**已删除功能的旧实现**，
等于白白把历史逻辑一起交付出去。`package_deploy.py` 已内置 `target`/`dist` 清理。

### 2.3 已完成的验证（2026-10-13）

**成品**：`release/caseflow-deploy-1.0.0-20261013-235038.zip`（122.6 MB，274 个文件）

模拟一台**没装 Java、没装 MySQL** 的全新电脑，解压后实测：

| 验证项 | 结果 |
|---|---|
| 目录完整性 | 12 个顶层项齐全，占位文件到位 |
| jar 敏感项 | 已剔除（前端 js 仅 29 个，非历史的 672 个） |
| **包内自带 Java 启动** | `Started CaseFlowApplication in 2.483 seconds` |
| profile 自动降级 | 口令未填 → 自动走 trial 试用模式（H2，免 MySQL） |
| 前端首页 | 成功（922 字节） |
| 管理员登录 | 成功（boss/admin123） |
| 案件管理接口 | `code=0` |
| 前端 JS/CSS 资源 | JS 1105 KB、CSS 380 KB 正常加载 |
| 源码残留自检 | 无 `.java/.vue/.py/.map/node_modules/pom.xml/.db` |

**验证中踩的坑**：

1. **剔除 `schema.sql` 后直接启动会失败**，报
   `No schema scripts found at location 'classpath:sql/schema.sql'`。
   根因是 `application.yml` 写死了 `spring.sql.init.schema-locations`，脚本缺失时 Spring
   抛异常终止（不是静默跳过）。外置配置必须加：

   ```yaml
   spring:
     sql:
       init:
         mode: never
   ```

   正式库由 DBA 用随包的 `建库脚本/schema.sql` 提前建好，不依赖应用启动时自动建表。

2. **zip 不保存空目录**，`logs/`、`data/uploads/` 解压后不存在，
   会导致附件上传和日志重定向失败。已用占位 `说明.txt` 解决（脚本注释里有说明，别删）。

3. **`characterEncoding` 必须是 Java 字符集名 `UTF-8`**，写成 MySQL 的 `utf8mb4`
   会被 Connector/J 8 直接拒绝：`Unsupported character encoding 'utf8mb4'`。

### 2.4 配置外置

把 `application-mysql.yml` 从 jar 里拿出去，放到 `config/`，
启动时用 `--spring.config.additional-location` 指定：

```bat
runtime\bin\java -jar case-flow-backend.jar ^
  --spring.config.additional-location=file:./config/ ^
  --spring.profiles.active=prod
```

这样**数据库口令写在交付方的配置文件里，不在你的 jar 里**。

> 顺带修掉默认口令问题：正式库务必用强口令，
> 不要沿用 `caseflow/caseflow`。见 `生产化改造指南.md` 第 1.2 节。
> 交付包里的 `config/application-prod.yml` 已把口令位置留成中文提示，
> 强迫部署方必须填写，不会默默用默认值上线。

## 3. 第二层：代码混淆（建议做）

在 jar 上跑一道 ProGuard，类名方法名变成 `a.b.c`，包名变成 `x.y`。
**说清楚它做不到什么**：不加密字节码，CFR 仍能还原逻辑，只是阅读成本大幅上升。
它的价值在于——让"看懂并二次开发"从几分钟变成几小时甚至几天。

### 3.1 接入方式

`pom.xml` 里加 `proguard-maven-plugin`，并在 `package` 之后执行
（顺序很重要：先由 Spring Boot repackage 生成 fat jar，再混淆 jar 内
`BOOT-INF/classes` 下的字节码，最后重写 zip）。

### 3.2 本项目的特殊之处（好消息）

我检查过代码，**这个项目对混淆非常友好**：

- ✅ 几乎没有反射调用——全项目只有两处 `getMethod` 相关的拦截器 OPTIONS 判断，
  不是动态方法调用
- ✅ 没有 SpEL / OGNL / 表达式求值
- ✅ 实体类都带 `@TableName`/`@TableId` 显式标注，不依赖类名推断
- ✅ 接口返回 `VO`，不直接序列化实体，字段名可以安全混淆

**需要 keep 的地方**：

```proguard
# Spring 组件：注解 + 类不能改名
-keep @org.springframework.stereotype.Component class * { *; }
-keep @org.springframework.web.bind.annotation.RestController class * { *; }

# 实体：MyBatis-Plus 靠注解定位表，但字段名参与 SQL 映射，需保留字段
-keep class com.caseflow.entity.** { *; }

# VO/DTO：Jackson 序列化靠 getter 名字，前端强依赖字段名，必须原样保留
-keep class com.caseflow.vo.** { *; }
-keep class com.caseflow.dto.** { *; }

# 枚举：DictHolder 用名称查字典，混淆后前端拿不到中文标签
-keepclassmembers enum * { *; }

# 异常与注解保留
-keepattributes *Annotation*,Signature,Exceptions,InnerClasses
-dontwarn org.springframework.**
-dontwarn com.baomidou.**
-dontwarn javax.annotation.**
```

> ⚠️ **VO/DTO 必须保留字段名**，因为前端 JS 直接按字段名取值。
> 这意味着"数据接口长什么样"是可见的——这是 Web 系统的固有特性，
> 无法也不必隐藏。**要保护的是 Service 层的业务逻辑，不是字段名。**

### 3.3 验证要求

混淆后**必须跑完整回归**，不能只看"能启动"：

```bash
# 后端
.venv\Scripts\python.exe scripts\verify_todo_ingest.py
.venv\Scripts\python.exe scripts\verify_undo.py
.venv\Scripts\python.exe scripts\verify_flow.py
# 前端 e2e（需前端在 5173 跑着）
node scripts\cf-e2e-todo-consistency.mjs
```

启动时重点看有没有 `ClassNotFoundException` / `NoSuchMethodException` /
`BeanCreationException`——这些正是 keep 规则漏了的表现。

## 4. 第三层：授权与防复制

混淆防不住"拷贝到另一台机器"。要防复制得靠授权校验。

### 4.1 机器码绑定

思路：启动时采集本机特征（Windows MachineGuid / 主板序列号 / 磁盘卷序列号）
计算指纹，与授权文件里的指纹比对，不匹配就拒绝启动。

```
首次部署：客户端生成「申请码」→ 你这边签发「授权文件」→ 放回 config/
每次启动：读授权文件 → 比对本机指纹 → 不符则拒绝服务并写日志
```

**注意**：这类代码一旦开源就等于失效，所以授权逻辑本身**不要进 Git**，
或者混淆后再打包。

### 4.2 到期控制

授权文件里带 `expireDate`，到期后拒绝启动。
适合按年收费的交付模式。

### 4.3 现实提醒

**技术手段只能提高门槛，无法杜绝。**对于内网系统（尤其是公安/政务内网），
真正的防线通常是：

- 合同约定（保密条款 + 禁止反编译条款 + 违约责任）
- 部署在你能控制或至少知情的物理环境
- 数据留在对方本地、不外传

技术手段的作用是让"泄露了也没法直接用、用了也追得到"，而不是"绝对不可能"。

## 5. 交付前检查清单

发包之前逐条确认：

- [ ] 交付目录里**没有** `.java` / `.vue` / `.py` / `pom.xml` / `package.json`
- [ ] 交付目录里**没有** `tools/`、`node_modules/`、`.venv/`
- [ ] 交付目录里**没有** `caseflow.mv.db`（演示库）
- [ ] 交付目录里**没有** `release/*-source-*.zip`
- [ ] jar 内**没有** `application-dev.yml`（H2 控制台）
- [ ] jar 内**没有** `sql/*.sql`（建表脚本）
- [ ] 数据库口令在 `config/` 里，**不在** jar 里
- [ ] 正式库口令已改掉默认的 `caseflow/caseflow`
- [ ] jar 已 ProGuard 混淆，且**全量回归已通过**
- [ ] 前端 dist 内无 `.map` 文件
- [ ] 已做一次「反编译抽查」，确认读不出关键业务逻辑

## 6. 建议的推进顺序

| 步骤 | 状态 | 说明 |
|---|---|---|
| 第一层：交付包瘦身 + jar 剔除敏感项 + 配置外置 + clean 构建 + 出包自检 | ✅ **已完成** | 跑 `scripts/package_deploy.py`，已在模拟全新电脑上端到端验证 |
| 第二层：ProGuard 混淆 | ⬜ 未做 | 方案与 keep 规则见第 3 节，需接入 pom 并跑全量回归 |
| 第三层：机器码绑定 + 到期校验 | ⬜ 未做 | 仅按年收费的商业交付才需要 |

**成品**：`release/caseflow-deploy-1.0.0-20261013-235038.zip`（122.6 MB）
目标机只需：解压 → 双击 `启动.bat` → 浏览器访问。未装 Java、未装 MySQL 也能跑起来
（自动降级试用模式）。

**下一步最值得做的是第二层。**第一层已经把"交源码"这个最大的坑堵住了，
剩下的泄露路径就是反编译 jar。加混淆后，读懂业务逻辑的成本从几分钟升到几小时以上。

如果暂时不打算加混淆，也**必须**执行第 5 节的检查清单后再发包——第一层已能覆盖绝大多数交付场景。
