# 案件流程流转与阶段任务管理

> 2026-10-04 落地。流程定义在 `app/backend/src/main/java/com/caseflow/flow/CaseFlowTemplate.java`，
> 执行引擎在 `app/backend/src/main/java/com/caseflow/service/FlowService.java`。
> 后续细化取保流程或调整工作分工时**只改模板类**，不动引擎与前端。

---

## 一、三层数据结构

```
Stage（阶段）→ Step（环节）→ Task（任务）
 初查          接收材料       接收刑事案件材料并登记
                立案           核对材料清单并签字接收
                侦查           填写立案登记表
                …              …
```

| 概念 | 载体 | 字段 |
|---|---|---|
| **Stage 阶段** | 案件 | `case_info.flow_stage` |
| **Step 环节** | 任务归类标签 | `case_plan.step_key` |
| **Task 任务** | 一行 `case_plan` | 一行=一个可勾选任务 |
| 标准任务标记 | 任务 | `case_plan.task_key` + `is_std=1` |

### 表结构调整（复用 `case_plan`，不新建表）

```sql
case_info  + flow_stage  VARCHAR(24) NULL   -- INITIAL/DETAIN/BAIL/CLOSED
case_plan  + stage       VARCHAR(24) NULL   -- 所属阶段
case_plan  + step_key    VARCHAR(32) NULL   -- 所属环节
case_plan  + task_key    VARCHAR(32) NULL   -- 标准任务标识（幂等去重用）
case_plan  + is_std      TINYINT     DEFAULT 0  -- 1=模板生成
```

原「侦查计划」直接升格为「阶段任务」——避免两套表并存、职责重叠。

## 二、刑事流程

```
┌─ 初查 INITIAL ──────────────────────────────────────────────┐
│  接收刑事材料 → 立案 → 侦查 → 反馈是否符合刑拘条件 → 刑拘  │
└────┬────────────────────┬─────────────────────┬─────────────┘
     │ 全部完成            │ 提前分流            │ 不批捕
     ▼                    ▼                     ▼
┌─ 刑拘在办 DETAIN ──┐  ┌─ 取保及监居 BAIL ─┐  ┌─ 已终结 CLOSED ─┐
│ 指派清案民警       │  │ 执行取保/监居     │  │ 释放 → 办结     │
│ → 逮捕 → 清案结束 │  │ （流程后续细化）  │  └─────────────────┘
└───┬─────────┬──────┘  └──────────────────┘
    │逮捕     │取保/释放
    ▼         └────────► BAIL / CLOSED
  CLOSED
```

## 三、行政流程

```
初查 INITIAL：接收材料 → 立案 → 侦查 → 呈批材料 → 批准行政处罚 → CLOSED
```

行政不走「刑拘在办」阶段。出口动作是 `PUNISH`（批准行政处罚）而非 `DETAIN`。

---

## 四、各阶段进入/退出与分支

| 阶段 | 进入条件 | 退出条件 | 可选分支 |
|---|---|---|---|
| **INITIAL 初查** | 刑事/行政立案 | 本阶段任务全 DONE（或领导提前分流） | 刑事：`DETAIN`刑拘 / `BAIL`取保 / `RELEASE`释放<br>行政：`PUNISH`批准处罚 |
| **DETAIN 刑拘在办** | 初查流入且动作为刑拘 | 指派+逮捕完成 | `ARREST`逮捕结案 / `BAIL`转取保 / `RELEASE`释放 |
| **BAIL 取保及监居** | 任一阶段以取保动作转入 | 环节全 DONE（细化后调整） | `CLOSE`解除收案 |
| **CLOSED 已终结** | 逮捕/释放/处罚/解除 | 终态，不可再流转 | 无 |

**流转触发**：**需领导确认**（`AuthContext.isFullAccess()`）。
任务全完成时界面提示"可以流转"，但不强拦 —— 提前终止/分流是真实业务。
每次流转必须显式选择分支（刑拘/取保/释放后果完全不同）。

**流转时自动同步强制措施**：转取保/监居 → `case_measure=BAIL`；转刑拘 → `DETENTION`，
保证盯办模块的措施期限能对上。

## 五、进度计算与重置

```
阶段进度 = 该阶段 DONE 任务数 / 该阶段任务总数
```

**不落库，永远实时算。** 这是"重置"能自动正确的根本原因：

流转时在**同一个事务**内做三件事：

1. 旧阶段任务全部置 `CANCELLED`（退出进度分母）
2. 改 `case_info.flow_stage`
3. 按模板生成新阶段任务（状态全部 `PENDING`）

→ 分母换成新阶段任务、分子为 0，**进度天然归零**。

因此系统里**不存在"重置进度"这个动作**，也就不会出现
"忘了调重置接口导致进度虚高"的历史包袱。任一步失败整体回滚，不会留半截状态。

**已终结阶段**进度恒 100%（避免"办结了还显示 60%"的观感问题）。

### 与既有状态机的关系（并存不冲突）

| 字段 | 管什么 | 状态机 |
|---|---|---|
| `flow_stage` | 走到哪个阶段、进度多少 | 本流程 |
| `investigation_status` | 侦查终结要不要领导审批 | 盯办 START→SUBMIT→APPROVE |

两者**各自独立演进**，流转不会改动 `investigation_status`，审批也不会改阶段。

## 六、存量数据兼容

| 场景 | 处理 |
|---|---|
| `flow_stage` 为 NULL | 按 `INITIAL`（初查）处理 |
| `case_plan.stage` 为 NULL | 归入「初查 / 侦查」环节参与进度，老案件完成率依然可见 |
| `is_std=0` | 存量与民警自建任务都是 0，只有模板任务为 1 |
| 老案件进度 | 不受升格影响，`planStats` 与 `FlowService` 用同一套归位口径 |

**排序兼容**（拖拽功能遗留）：`ORDER BY CASE WHEN sort_order IS NULL THEN id ELSE sort_order END`，
存量 NULL 回退按 id。

## 七、扩展机制（后续补充流程用）

### 加一个环节
改 `CaseFlowTemplate` 两处即可：

```java
// 1) STEP_TASKS 里加该环节的标准任务
m.put(STEP_MY_NEW, Arrays.asList("任务一", "任务二"));

// 2) CRIMINAL_STEPS / ADMIN_STEPS 里把环节插入到对应阶段的顺序
c.put(STAGE_DETAIN, Arrays.asList(STEP_ASSIGN_CLEAR, STEP_MY_NEW, STEP_ARREST, STEP_CLOSE));
```

### 细化取保流程
现在 `BAIL` 阶段只有「执行取保/监居」入口环节。细化时：

1. 在 `STEP_TASKS` 补 `EXECUTE_BAIL` 的后续环节任务
2. 在 `CRIMINAL_STEPS[STAGE_BAIL]` 里补环节顺序
3. **存量取保案件调`POST /watch/cases/{id}/flow/seed`** 补生成新任务
   （按 `task_key` 幂等去重，不会重复生成，也不会动已有任务）

### 调整工作分工
环节与任务都是纯数据，加人名/角色标签只需在 `STEP_TASKS` 的任务文案里体现，
不需要改引擎。

## 八、接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/watch/cases/{id}/flow` | 登录即可 | 流程视图：环节顺序+每环节任务+进度+可流转分支 |
| GET | `/api/watch/cases/{id}/flow/progress` | 登录即可 | 仅进度（单案轮询用） |
| POST | `/api/watch/cases/{id}/flow/transfer` | **管理层** | 阶段流转，事务+留痕 |
| POST | `/api/watch/cases/{id}/flow/seed` | 管理层 | 补全本阶段标准任务（幂等） |
| POST | `/api/watch/plans/{id}/revert` | 承办人/管理层 | 撤销完成（勾选框双向切换） |

**流转留痕**：写 `operation_log`，action=`FLOW_TRANSFER`，可撤回（快照含 plans 列表）。

## 十、任务勾选权限（分两级）

| 任务类型 | 承办人 | 管理层 | 理由 |
|---|---|---|---|
| **标准任务**（`is_std=1`，模板生成） | 可勾 | **可勾** | 代表全所统一的必经环节；领导看到某环节未完成需能直接确认完成，否则进度永远卡 99%、流转永不触发 |
| **民警自建任务**（`is_std=0`） | 可勾 | 只读 | 这是民警自己的工作安排，领导不该替办案人"安排工作"或"勾掉工作"——盯办模块原有的权限边界，予以保留 |
| 增 / 删 / 改任务、`cancel` | 可操作 | 只读 | 属"安排/移除工作"，不放开 |

实现：`PlanService.checkStdOrAssignee()`，只挂在 `done` / `revert` 两个动作上。

## 十一、已知坑（已修，勿重犯）

### 1. MyBatis-Plus 的 `apply()` 不能拼排序
```java
.apply("(CASE WHEN sort_order IS NULL THEN id ELSE sort_order END) ASC, id ASC")   // ❌
```
`apply()` 拼进的是 **WHERE 条件**，会生成
`WHERE (case_id=? AND (CASE ... END) ASC, id ASC)` → H2 直接报语法错。

```java
.last("ORDER BY (CASE WHEN sort_order IS NULL THEN id ELSE sort_order END) ASC, id ASC")   // ✅
```

### 2. 进度口径必须与流程面板一致
`WatchService.planStats()` 原来统计**全部**非取消任务。
案件流转到刑拘在办后，存量计划（`stage` 为 NULL）若不按阶段归位会继续计入分母，
导致列表页进度虚高、且与流程面板数字对不上。
现统一用「`stage` 为 NULL 视为 INITIAL」，与 `FlowService` 同一套口径。

### 3. 已有业务规则可能与新流程冲突
原`checkOperate` 硬性规定「计划只能承办人操作，管理层只读」，
与流程面板的"领导确认流转"设计矛盾。**不要直接删规则**——
按任务性质分级（标准 vs 自建）既保住原设计意图，又让流程跑得通。

### 4. 列表页进度别用 N+1 请求
`CaseVO` 已带 `flowStage` / `flowStageName` / `planDone` / `planTotal`，
随列表一次返回。`flow/progress` 端点只留给单案轮询用。
