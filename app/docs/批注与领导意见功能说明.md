# 办理进度批注 · 领导意见与落实反馈 · 盯办权限调整

> 2026-10-02 上线。本文档说明四项功能的角色权限、操作流程与数据模型。

## 一、角色与权限总览

系统的角色分四类（沿用 `Roles.java` 既有划分）：

| 业务角色 | 系统角色代码 | 说明 |
|---|---|---|
| **管理员** | `BOSS` 系统管理员 | 管理端 |
| **领导** | `CHIEF` 所长 / `DEPUTY_CHIEF` 副所长 / `LAW_OFFICER` 法制员 | 管理端 |
| **办案人** | 任一角色，但须是**本案 `case_assignee.status=ACTIVE` 的员工**（主办/协办）所绑定的账号 | 工作执行者 |
| **普通用户** | `STAFF` 普通民警（未承办本案） | 只读 + 自己名下案件 |

各功能权限矩阵：

| 功能 | 管理员 | 领导 | 办案人（本案承办中） | 普通用户 |
|---|---|---|---|---|
| 查看批注 / 意见 | ✔ | ✔ | ✔ | ✔ |
| **新增/编辑/删除批注** | ✔ | ✔ | ✘ | ✘ |
| **提出意见（多条）** | ✔ | ✔ | ✘ | ✘ |
| **反馈意见落实情况** | ✘ | ✘ | ✔（仅限本人承办的案件） | ✘ |
| **开始侦查** | ✘ | ✘ | ✔（仅限本人承办的案件） | ✘ |
| **新增/编辑/完成/取消侦查计划** | ✘ | ✘ | ✔（自己给自己指定） | ✘ |
| 查看侦查计划 | ✔ | ✔ | ✔ | ✔ |
| 登记/变更强制措施 | ✔ | ✔ | ✘ | ✘ |
| 同意终结 / 退回补侦 | ✔ | ✔ | ✘ | ✘ |

设计原则一句话：**过程动作归办案人（开始侦查=「我开始干了」，计划=「我给自己排的活」），监督与终审归管理端（批注、意见、审批）**。前端隐藏按钮只是体验层，真正的拦截全部在服务端（403 + 明确提示语）。

## 二、功能1：办理进度批注

类似 Word 批注：管理端可以在**每条办理进度**（时间线上的任意一条记录）下面挂旁注，不改动进度本身。

- **入口**：案件详情抽屉 → 「办理进度」时间线，每条记录下有「批注 / 追加批注」按钮（仅管理端可见；已撤回的进度不可批注）。
- **展示**：批注以左竖线浅底卡片挂在对应进度下方，展示**批注人、批注时间、内容**；编辑过的还显示「最后编辑人 · 时间」。按 `log_id` 与进度关联。
- **管理**：管理端对每条批注可「编辑」「删除」；删除有确认弹窗。
- **留痕**：批注的增/改/删全部进入操作日志时间线（动作名：进度批注 / 编辑批注 / 删除批注）。
- **与撤回体系的关系**：批注**不进**案件快照——撤回某条进度不会连带回滚批注（旁注语义）；因此批注类日志也不可撤回。

## 三、功能2：领导意见与完成确认

- **提出**：管理端在案件详情抽屉或盯办抽屉的「领导意见」面板点「提出意见」，可对同一案件提出**多条**，每条独立编号、独立反馈。
- **反馈**：办案人（本案承办中）对每条意见点「反馈落实情况」，标记三态之一：
  - `DONE` 已完成 / `IN_PROGRESS` 进行中 / `NOT_DONE` 未完成；
  - 可附落实说明；**反馈时间由服务端生成**（防止前端伪造时间线）；
  - 反馈可再次提交覆盖更新（每条意见保留最新一次反馈；反馈历史在时间线可查）。
- **展示**：意见卡上显示状态标签、反馈人、反馈时间、反馈说明全文。
- **越权拦截**：非本案承办人反馈 → 403「只有本案承办人可以反馈意见落实情况」；管理端也不代办反馈（落实是办案人的责任）。

## 四、功能3：意见回复的提交提示语（上传声明）

反馈弹窗中**取消佐证材料上传**，改为一句结构化「上传声明」，布局如下：

```
┌ 反馈落实情况 ──────────────────────────────┐
│ 意见原文（引用块）                            │
│ 落实状态   (●完成) ( 进行中) ( 未完成)         │
│ 落实说明   [选填文本框…]                      │
│ ┌ 上传声明（代替上传佐证材料，选填）———————   │
│ │ 请输入：于[2026-10-02 01:20:00 ▾]（不选则  │
│ │ 默认当前时间，精确到秒）在[一体化办案平台▾]  │
│ │ 上传了[到案经过情况说明.docx] 。            │
│ │ 常用平台：一体化办案平台 · 全国公安信息平台… │
│ │ 将并入说明：于…在…上传了…。（实时预览）      │
│ └───────────────────────────────┘          │
│                     [取消] [提交反馈]        │
└────────────────────────────────────────────┘
```

字段与默认值逻辑：

| 字段 | 控件 | 默认值 / 约束 |
|---|---|---|
| 上传时间 | `el-date-picker` datetime，`YYYY-MM-DD HH:mm:ss` | 打开弹窗时默认**当前时间（精确到秒）**；点击即改；提交时若被清空，兜底取提交时刻 |
| 平台名称 | 文本框 + 常用平台一键填入（一体化办案平台 / 全国公安信息平台 / 电子卷宗系统 / 执法办案系统） | 空 |
| 文件名称 | 文本框 | 空 |

- **拼装规则**：平台与文件**任一**填写即生成声明句 `于 {时间} 在 {平台} 上传了 {文件}。`，实时预览；提交时并入反馈说明（说明正文 + 换行 + 声明句）。
- **成对校验**：平台与文件只填其一会被拦截（避免产出"在（待填平台）上传了…"的残缺声明）；两项都留空则不生成声明句，只提交说明。
- 整个流程**不调用任何文件上传接口**。

## 五、功能4：案件盯办权限调整

1. **开始侦查由办案人本人点击**。语义 = 「我开始干了」，是工作者的自我认领，不由领导决定。
   - 后端：`ApprovalService.transition(START)` 由原来的「承办人或管理层」收紧为**仅本案现职承办人**；
     管理端触发返回 403「该操作由办案人本人执行（管理层不代点：开始侦查表示办案人开始工作）」。
   - 前端：案件详情抽屉与盯办抽屉中，「开始侦查」按钮仅对本案办案人显示；管理端看到灰字提示「由办案人本人点击开始侦查」。
   - `提请审批（SUBMIT）`暂保持「办案人或管理端」均可，如需一并收紧到办案人，改 `ApprovalService` 一处即可。
2. **侦查计划由办案人自建**（自己给自己指定的计划）。
   - 后端：`PlanService` 写操作（新增/编辑/完成/取消）去掉管理端旁路，仅本案现职承办人；
     管理端触发返回 403「侦查计划由办案人自行制定，管理层仅可查看」。
   - 前端：盯办抽屉中「新增计划 / 编辑 / 取消 / 勾选完成」仅对办案人显示；管理端只读，并显示说明文字。
3. **管理端负责最终审批与提出意见**：审批流（同意终结 / 退回补侦）维持管理端专属不变；新增的「提出意见」「批注」也归管理端。

## 六、数据模型

```
case_progress_comment          办理进度批注
├─ id / case_id / log_id       log_id → operation_log.id（关联进度）
├─ content                     批注内容
├─ creator_id / creator_name   批注人（冗余姓名）
├─ created_at                  批注时间
└─ updated_at / updater_name   最后编辑

case_leader_opinion            领导意见与落实反馈
├─ id / case_id / content
├─ creator_id / creator_name / created_at      提出人（管理端）与提出时间
└─ feedback_status / feedback_note             最新反馈：DONE / IN_PROGRESS / NOT_DONE（NULL=未反馈）
   feedback_by / feedback_by_name / feedback_at  反馈人与反馈时间（服务端生成）
```

- 两张表均为 `CREATE TABLE IF NOT EXISTS`，启动自动补建；均**不进案件快照体系**（旁注语义，不随撤回回滚）。
- 修复的既有缺陷：`sql/schema.sql` 此前在 `app/sql/` 与 `backend/src/main/resources/sql/` 各存一份且无同步机制
  （本次改了前者、启动时建不出新表）。已改为 pom 资源映射 `../sql → classpath:/sql/`，删除副本，**真正单一数据源**。

## 九、领导意见增强（2026-10-04）

在原有「提出意见 / 反馈落实」基础上，补齐序号、排序、时限、分级、预警与流程图六项能力。

### 9.1 数据结构

`case_leader_opinion` 新增 3 列，**全部可空**（兼容旧数据，见 9.5）：

| 列 | 类型 | 含义 |
|---|---|---|
| `sort_order` | INT NULL | 拖拽排序位次，1 起连续。NULL=旧数据 |
| `deadline` | DATETIME NULL | 落实截止时间，可空 |
| `importance` | VARCHAR(4) NULL | A=最重要 / B=重要 / C=一般，NULL 视为 C |

登记在 `SchemaMigration.NEW_COLUMNS`，老库启动时幂等补列。
**紧急性（正常/临期/已逾期）不落库**，由 `deadline` 与当前时间实时算出，避免定时刷新导致状态过期。

### 9.2 序号规则

- 显示序号 = **前端数组下标 + 1** 实时计算，不读库。
  因此插入、删除、拖拽之后编号自动重算，**结构上不可能断号或重复号**。
- `sort_order` 只负责持久化顺序，不参与显示编号——这是"永不断号"的关键。

### 9.3 拖拽排序

- 前端 `sortablejs`，把手在行尾（`⋮⋮`），**仅管理层 + 仅桌面端**启用
  （手机端触摸拖拽体验差，且顺序属领导语义）。
- 拖拽结束先本地重排数组（序号立即刷新、无等待感），再 `POST /opinions/reorder` 落库；
  保存失败自动 `reload()` 回滚，避免界面与库不一致。
- 后端按提交的 id 数组写 `sort_order` 1..N，跨案 id 会被跳过，提交数组缺项时剩余项补到末尾，保证连续。

### 9.4 截止时间 / 重要性 / 紧急性

- 截止时间与重要性在**录入行**可填，也可在**列表内就地修改**（管理层）。
- 紧急性阈值 `URGENT_HOURS = 48`：
  - `已逾期`：截止时间已过
  - `临期`：距截止 ≤ 48 小时
  - `正常`：其余，**以及无截止时间的条目**
- 配色：左侧色条（逾期红 / 临期橙 / 正常透明）+ 文字角标。
  **不把整块背景染成深色**——沿用原有深色文字保证小屏可读；
  且颜色之外一律另带文字，不靠颜色单独承载信息（色盲可读）。

### 9.5 向后兼容

| 场景 | 处理 |
|---|---|
| 旧数据 `sort_order` 为 NULL | 读取时按 `id` 升序回退；`OpinionService.initSortOrderIfAbsent` 在整批均为 NULL 时惰性初始化 1..N 并落库（幂等） |
| 旧数据 `importance` 为 NULL | 前端 `importanceOf()` 归一为 C（一般），后端 `normalizeImportance()` 同样回落 C，非法值也不入库 |
| 旧数据 `deadline` 为 NULL | 紧急性判定为「正常」，列表不显示截止时间 |
| 排序 SQL | `ORDER BY CASE WHEN sort_order IS NULL THEN id ELSE sort_order END ASC, id ASC`，作用在已有列上，不需额外迁移 |

### 9.6 工作流程图

- 位置：面板头「工作流程图」按钮，**可折叠、默认收起**（意见多时不挤占列表空间）。
- 形态：纵向流转链，节点=意见、箭头=流转顺序；节点色=紧急性（已完成转绿），
  A 级加金色描边；节点内三行显示「序号·等级 / 内容摘要 / 截止与状态」。
- **领导与员工看同一份数据**（都来自 `GET /opinions`），差异只在可编辑性：
  - 员工（本案承办人）：点节点直接打开反馈弹窗更新状态
  - 领导：点节点提示当前状态与责任人，只读看整体进度
- 容器高度 `max(260, 条数 × 92 + 60)` 写死 + `EChart height="100%"`，
  沿用项目「列表类容器必须写死高度」的约定，避免 flex 循环依赖把面板顶爆。

### 9.8 实现坑（已修，勿重犯）

1. **`EChart.vue` 原本只注册了 Bar/Line/Pie/Tree**，没注册 `GraphChart`——
   用 `type:'graph'` 会**静默不渲染**（容器在、canvas 无、控制器零报错）。
   已在 `echarts.use([...])` 补上 `GraphChart`。
2. **`layout:'none'` 的 graph 只认数值坐标**，`x:'50%'` 会让整图不渲染。
   改为 `flowCenterX` 计算像素值，按容器宽度取中并随展开/条数变化重算。
3. **props 在脚本里必须写 `props.isFullAccess`**，
   裸写 `isFullAccess.value` 报 `ReferenceError`（模板里才能自动解包）。
   已统一为计算属性 `isManager`。
4. 流程图容器 `v-if` 刚展开时可能量不到宽度，`watch(flowOpen)` + `nextTick` 补测一次。

### 9.9 移动端

- 拖拽把手不渲染（`:class="{ 'is-mobile-full': isMobile }"` 让时间控件占满整行）。
- 流程图、序号、紧急性、重要性展示在手机端完全一致；反馈入口仍是仅本案承办人可见。

## 十、办案组别与指派约束（2026-10-04）

### 组别定义

| 值 | 名称 | 可承接 |
|---|---|---|
| `INITIAL` | 初查组 | 初查任务 |
| `CLEAR` | 清案组 | 刑拘在办 |
| `NONE` | 不限 | 各类案件（空值/非法值一律归一为此） |

**取保及监居刻意不限制** —— 它既不是初查也不是清案，限制会让案件无处可派。

### 数据来源：员工档案是权威

组别校验以 **`org_employee.police_group`** 为准，不是账号：
指派选的是「员工」，组别理应挂在员工档案上。`sys_user.police_group`
只用于注册时强制选择 + 管理员审核时确认；有些账号（如 boss）根本没有员工档案，
用它校验会漏掉真实约束。

### 组别推导（前后端必须一致）

`CaseService.moduleOf` 按 `case_measure` 判定：
`DETENTION` → 清案组；无措施 / `NONE` / `BAIL` / `RESIDENCE` → 不限。
**与列表页 `module` 过滤口径一致**，否则会在刑拘在办页签里选人却被提示初查组限制。
前端 `AssignDialog.requiredGroup` 用同一套规则。

### 三处入口都要能设组别

| 位置 | 何时必填 |
|---|---|
| 注册页 | 普通民警（`applyRole=STAFF`）必选 |
| 账号管理开通/审核 | 普通民警必选，管理员可帮纠正 |
| 员工图谱编辑 | 随时可改 |

### 指派时的双重把关

1. **前端置灰**：`EmployeePicker` 收到 `requiredGroup` 后，不匹配的员工
   **置灰不可选 + 显示原因**「只能由清案组人员承办」——
   隐藏会让人以为系统里没别人、以为流程走不通。
2. **后端拦截**：`CaseService.assign` 强制校验，报错带双方组别与姓名：
   > 「清案组」只能指派给清案组人员；陈组员 属于「初查组」

### 民警负荷详情

盯办详情点主办人/协办人名字打开，返回：
主办/协办/合计数、已超期数、3 天内到期数、阶段分布、逐案概要
（编号+名称+角色+阶段+任务进度+期限）。
排序：主办优先 › 已超期优先 › 期限近的优先。
**只返回案件概要不含案情细节**，避免横向信息泄露。

### 存量兼容

`police_group` 可空，NULL 视为「不限」——存量员工不改也能继续被指派。
上线即瘫痪比放宽规则更糟。

### 坑

负荷详情排序里把 `daysLeft` 强转 `Long`，但它 put 进去是 `Integer`，
运行期抛 `ClassCastException`。**`Map<String,Object>` 取值时强转必须与
put 时的实际类型一致。**
