# 案件附件存储方案

> 面向场景：单位内网共享使用（10–50 人），服务器可能是 Windows Server，也可能完全物理隔离。
> 本文回答三个问题：**现在是怎么存的**、**有什么风险**、**分几步改成什么样**。

---

## 一、先回答你最关心的：数据库要不要上线？内存够不够？

**结论：内存够，不用为数据库单独买机器；但"上线"这个词要拆成两件事看。**

已经实测过这台机器的资源：

| 项目 | 实测值 | 判断 |
|---|---|---|
| 物理内存 | 31.6 GB | 充裕 |
| 当前可用 | 15.6 GB | 充裕 |
| CPU 核心 | 20 核 | 充裕 |

跑这套系统的实际占用：

| 进程 | 常驻内存 | 说明 |
|---|---|---|
| Java 后端 | 约 400–700 MB | 已用 `-Xmx1536m` 限死上限，不会无限涨 |
| MySQL | 约 300–500 MB | InnoDB 缓冲池可配，50 人规模 256MB 足够 |
| 合计 | **约 1 GB 以内** | 占用不到你可用内存的 7% |

所以：**数据库不需要"上线"到别的机器，就跟后端装同一台就行。** 50 人的单位，同时在线通常不到 10 人，日增数据也就几十 KB 到几 MB，单机 MySQL 完全撑得住，不需要主从、不需要集群。

需要上线的**不是数据库**，而是这两样：

1. **服务要能被别人访问** —— 这已经做完了，绑 `0.0.0.0:8080`，局域网 `http://192.168.2.118:8080/api/` 已验证可打开。
2. **备份要真的存在** —— 数据只有一份，磁盘坏了就全没了。这个比"上线"重要，见第四节。

## 二、现在附件是怎么存的

读了 `FileService` / `FileController`，现状是这样：

```
上传请求
   │
   ├─ 文件名重命名：{时间戳}_{8位随机}.{扩展名}   ← 防重名、防路径穿越，这点做对了
   ├─ 落盘路径：{upload-dir}/{yyyyMM}/{重命名后的文件}
   └─ 数据库 case_file 表只存元信息：
        file_name(原名) / file_type / file_size / storage_path(相对路径) / uploaded_by / uploaded_at
```

`case_file` 表**不存文件内容**，只存 `storage_path` 这个相对路径字符串。这是完全正确的做法 —— 见第三节"一个必须避开的坑"。

当前 `upload-dir` 来自配置项 `caseflow.upload-dir`，默认 `./data/uploads`（**相对路径**）。局域网启动时已经用 `--caseflow.upload-dir=D:/案件指派demo/data/uploads` 覆盖成了绝对路径，这一步是必须的：**相对路径会跟着启动目录漂移**，哪天从别的目录起服务，附件就全"丢失"了（其实是找错地方了）。

目录目前是空的（还没有真实上传），按月分目录 `yyyyMM`，结构如下：

```
D:/案件指派demo/data/uploads/
  └── 202609/
        └── 1759212345678_a1b2c3d4.pdf
```

磁盘空间：D 盘 200 GB，已用 42 GB，剩 159 GB。按单个案件材料平均 5 MB 算，够存约 3 万份。

## 三、风险清单（按严重程度排序，这才是要改的原因）

| # | 风险 | 后果 | 严重度 |
|---|---|---|---|
| R1 | **只有一份，没有异地副本** | 磁盘坏 / 误删 / 中勒索病毒 → 案件材料永久丢失 | 致命 |
| R2 | **没有版本与防篡改** | 附件可被直接覆盖或替换，事后无法证明"当时提交的就是这份" | 高（办案场景要害） |
| R3 | **删除是真删** | `Files.deleteIfExists` 物理删除，误删不可恢复 | 高 |
| R4 | **与代码同盘** | 附件和程序放一块，重装/迁移时容易被一起清掉 | 中 |
| R5 | **无配额、无类型白名单** | 有人传 2 GB 的视频就把盘塞满；`text/html` 上传后可能被当页面执行 | 中 |
| R6 | **上传无病毒扫描** | 内网 U 盘流转的文件带毒会传进来 | 中 |
| R7 | **文件名与大小写敏感** | Windows 上 `A.pdf` 与 `a.pdf` 同文件，Linux 上是两个 —— 未来换系统会出问题 | 低 |

**一个必须避开的坑：不要为了"省事"把附件写进数据库 BLOB 字段。**

新手很容易觉得"文件存数据库里最省心、备份一起备"。实际上：数据库文件会被附件撑到几十 GB，**备份变慢、恢复变慢、`SELECT *` 变慢**，而且数据库备份和附件备份从此绑死，无法独立扩容。业界标准做法就是现在这样 —— **数据库存元信息（路径/大小/哈希），内容存文件系统或对象存储**。你现在这个架构是对的，别改回去。

## 四、方案分档：按你的实际条件选

三档方案的差别是「文件的物理位置放哪儿」，**对代码的改动量却差不多**（都要做第五节的抽象）。

### 方案 A：本机独立数据盘 + 自动备份（最省事，10 人以内够用）

```
D:/案件指派demo/  ← 程序（可随时重装）
E:/caseflow-files/  ← 附件（独立盘，先挂一个数据盘）
F:/caseflow-backup/  ← 备份（另一个物理盘）
```

- **做法**：把 `--caseflow.upload-dir` 指向独立盘；加一个定时任务，每天凌晨把附件目录 + MySQL 的 `mysqldump` 一起打包，压缩后拷到第二个物理盘，保留最近 30 天。
- **好处**：不动代码，当天就能落地；程序重装不影响附件。
- **局限**：还是单机 —— 整台机器炸了就没了（但至少有备份盘）。
- **适合**：10 人以内、没有文件服务器、不想折腾。

### 方案 B：内网文件服务器 / NAS（推荐，最贴合你现在的环境）

```
应用服务器                    文件服务器 / NAS
┌──────────────┐             ┌────────────────────┐
│ Spring Boot  │──SMB/CIFS──▶│ \\fs01\caseflow\   │
│ 附件走共享目录 │             │  202609/xxx.pdf    │
└──────────────┘             └────────────────────┘
                                      │ 每日快照
                                      ▼
                             ┌────────────────────┐
                             │ NAS 自带 RAID + 快照 │
                             └────────────────────┘
```

- **做法**：把共享目录挂载/映射成本地盘符（Windows 上是 `net use Z: \\fs01\caseflow`），`--caseflow.upload-dir` 指向 `Z:/` 或直接用 UNC 路径。
- **好处**：文件不占应用服务器；NAS 一般都带 RAID 和快照，**R1/R2 一次性解决**；零代码改动。
- **代价**：需要一个 NAS 或一台闲置机器做文件服务器（单位一般都有）；网络抖动时上传会慢。
- **适合**：单位已有 NAS / 文件服务器 —— **如果你有，直接选这个。**

### 方案 C：对象存储（最规范，但要评估内网可达性）

对象存储是专门为"存海量文件"设计的服务，**天然带版本控制、防误删、生命周期归档、访问签名**，R1–R6 一次性全解决。

| 选型 | 适用条件 | 说明 |
|---|---|---|
| **MinIO 自建** | **完全物理隔离的内网** | 开源、单文件可跑、兼容 S3 协议、支持版本与桶策略。在内网任一机器上跑，附件全走它 |
| 阿里云 OSS / 腾讯云 COS | 服务器能出外网 | 免运维，但要通外网 + 持续付费 + 数据出内网需过审批 |
| 政务云对象存储 | 单位已有政务云 | 优先问一下单位 IT，通常已有统一存储服务，对接即可 |

> **重要提醒**：你之前明确说是**完全物理隔离**的网络。那么公网 OSS / COS 基本走不通（连不上、也不该连），**如果走对象存储这条路，只能是 MinIO 自建在内网**。

**MinIO 的性价比**：一个 20 MB 的可执行文件，内网机器上双击就能起，提供和阿里云 OSS 几乎一样的接口。以后万一单位上了政务云，代码一行不用改，只换配置里的 endpoint 就行 —— 这正是下一节要做抽象的理由。

## 五、改造方式：先抽接口，再换后端（不管选哪档都该做）

现在 `FileService` 里直接操作磁盘路径（`Files.createDirectories` / `file.transferTo` / `FileSystemResource`）。**要支持上面任何一种方案，第一步都是把这些操作抽到一个接口后面。**

```
                  ┌──────────────────────────┐
                  │  FileService（业务层不动）  │
                  │  upload / download / delete │
                  └────────────┬─────────────┘
                               │ 只调接口
                  ┌────────────▼─────────────┐
                  │  StorageService（接口）     │
                  │  put / get / delete / url  │
                  └────────────┬─────────────┘
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
      ┌──────────────┐ ┌──────────────┐ ┌──────────────┐
      │ LocalStorage │ │  NfsStorage  │ │  S3Storage   │
      │  本机目录     │ │ 共享盘/NAS    │ │ MinIO/OSS/COS│
      └──────────────┘ └──────────────┘ └──────────────┘
              由配置 caseflow.storage.type 决定装配哪个
```

**要点：**

1. **接口只有四个方法**：`put(key, inputStream)` / `get(key)` / `delete(key)` / `exists(key)`。够用了，别设计复杂。
2. **数据库 `storage_path` 字段的含义升级为「key」**：值是 `202609/1759212345678_a1b2c3d4.pdf` 这样的相对键，**不含任何盘符或目录前缀**。这样换存储后端时，数据库一行都不用改。
3. **`LocalStorage` 和 `NfsStorage` 实现可以共用**（共享盘挂成盘符后就是普通目录），实际只需写两个实现：`LocalStorage` + `S3Storage`。
4. **`S3Storage` 用 MinIO 官方 SDK**（或 AWS S3 SDK 指向 MinIO endpoint）。上传时直接流式传递，**不要先落本地临时盘再上传**，否则一次 100 MB 的上传要占双份磁盘 IO。
5. **删除改为"软删除"**：不物理删文件，改用对象存储的版本控制（或本地把文件移到 `_trash/` 并保留 90 天）。R3 就解决了。

**改动量评估**：新增 4 个文件（接口 + 3 个实现 + 配置），`FileService` 里替换约 6 处调用点，`FileController` 的下载改成 `storageService.get()` 后流式写出。**半天到一天的工作量，不影响现有任何业务逻辑。**

**迁移老文件**：加一个一次性任务，把 `storage_path` 指向的老文件从本地目录拷到新存储，**拷贝成功后再更新数据库**，不要先删后拷。留一份老目录只读快照，观察一到两周再清理。

## 六、顺带该补的几件小事（都是配置级，成本极低）

| 事项 | 做法 | 解决 |
|---|---|---|
| 类型白名单 | `FileService` 里已有的 `TYPE_MAP` 直接当白名单用，不在里面的直接拒 | R5 |
| 大小上限 | 后端 `spring.servlet.multipart.max-file-size` 现在是 100 MB，够；Nginx 那层记得同步设 `client_max_body_size 100m` | R5 |
| 配额 | 按用户/按案件统计已用空间，超阈值拒绝并提示 | R5 |
| 内容哈希 | 上传时算一次 SHA-256 存进 `case_file`，它同时是**去重依据**和**防篡改凭证** | R2 |
| 病毒扫描 | 内网部署一套 ClamAV，上传后异步扫，命中就标记文件为"可疑"并告警 | R6 |
| 下载审计 | 附件的每次下载也记一条 `operation_log`（现在上传/删除记了，下载没记） | 办案合规 |

其中**内容哈希（SHA-256）性价比最高**：加一个字段、一次计算，既能让重复上传的同一份材料不重复占空间，又能在事后证明"这份材料从上传到现在没被改过"。办案场景里这条相当有价值。

## 七、建议的落地节奏

| 阶段 | 做什么 | 什么时候做 |
|---|---|---|
| **第一步（现在）** | `upload-dir` 已改绝对路径 ✅；补一个每日备份脚本（附件 + `mysqldump`） | 立刻，这是底线 |
| **第二步（有 NAS 的话）** | 把 `upload-dir` 指到共享盘 / NAS，顺手解决 R1 的一半 | 随时，零代码 |
| **第三步** | 抽 `StorageService` 接口，`LocalStorage` + `S3Storage` 两个实现 | 等附件攒到一定量、或单位确定存储方案后 |
| **第四步** | MinIO 自建 + 老文件迁移 + 开版本控制 | 有明确需求时 |

**一句话总结**：内存和数据库都不用担心，一台机器装完事；**真正要防的是"附件只有一份"** —— 先加备份（第一步，今天就能做），再考虑换存储位置。代码上现在这套"数据库存路径、内容存文件"的架构是对的，只需要在外面加一层抽象，就能在未来平滑换到 NAS 或对象存储。
