# 案件盯办模块设计方案

> 版本：v1.0　2026-09-30
> 状态：待评审（评审通过后按第 9 节分期实施）
> 配套系统：CaseFlow 案件指派系统（已有：收案/指派/到期/办结/操作留痕/撤回/嫌疑人/类别字典）

---

## 1. 模块概述与定位

### 1.1 解决什么问题

现有系统管住了「收案 → 指派 → 盯到期 → 办结」的**流程**，但侦查过程的**执行质量**是黑盒：领导看不到案件查到哪一步、侦查计划定了没有、完成情况如何、强制措施是否临期。汇报反馈中"案件做到哪里、哪些没做""领导盯办"两条意见正对此症。

案件盯办模块把每个重点案件的侦查活动纳入「**计划 → 执行 → 预警 → 审批**」闭环，实现三类案件的分层管理：

| 子模块 | 案件范围 | 管理抓手 |
|---|---|---|
| 初查案件 | 尚未采取强制措施的核查案件（行政初查、刑事初查） | 嫌疑人资料、初查进展、类型化检索 |
| 刑拘在办 | 已刑拘、在侦查羁押期限内办理 | 侦查计划、批捕期限倒计时、进度跟踪 |
| 取保及监居 | 取保候审、监视居住 | 侦查计划、取保/监居期限（12个月/6个月）倒计时、进度跟踪 |

### 1.2 核心设计决策（先讲清楚，后面所有设计由此展开）

**决策一：不另建独立案件表，三大子模块是同一批案件的「动态视图」。**
一个案件的真实轨迹是：初查 →（立案/刑拘）→ 刑拘在办 →（批捕后）→ 移送审查起诉，或初查 → 取保/监居 → 移送。若按子模块建三张表，一个案件要在表间迁移，数据分裂、留痕断裂。
因此：案件本体仍是 `case_info`；用**强制措施字段（`case_measure`）**表达案件当前处于哪个子模块，子模块列表 = 按该字段过滤的视图。案件在子模块间流转即一次字段变更（留痕、可撤回）。

**决策二：侦查生命周期与现有指派状态正交，新增独立进度状态字段。**
现有 `status`（待指派/已指派/处理中/已办结/已撤销）描述**流程流转**；新增 `investigation_status`（待初查/侦查中/待审批/侦查终结）描述**侦查进度**，两者并行、互不干扰，互不破坏现有撤回快照体系。

**决策三：全部写操作复用 `operation_log` 快照留痕。**
`CaseSnapshot.info` 序列化整个 `CaseInfo` 实体，新增列自动进入快照，零成本获得新字段的撤回能力；侦查计划/审批另建表，删除类操作按既有约定记录快照。

## 3. 案件分类体系优化

### 3.1 分类维度总表

| 维度 | 字段 | 取值 | 说明 |
|---|---|---|---|
| 案件大类 | `case_type`（现有） | 未立案 / 刑事 / 行政 | 不变，新增案件强制必选 |
| 案件小类 | `category`（现有） | 由类别字典维护 | 刑事=电诈/接触性诈骗/故意伤害类/盗窃类/其他（已上线）；行政 8 项不变 |
| **侦查阶段** | `investigation_status`（新增） | 待初查/侦查中/待审批/侦查终结 | 全案件通用生命周期 |
| **强制措施** | `case_measure`（新增） | 无/刑拘/取保/监居 | 决定案件归属哪个盯办子模块 |

### 3.2 三大子模块的过滤口径（视图定义）

| 子模块 | 过滤条件 |
|---|---|
| 初查案件 | `case_measure = 'NONE'` 且 `status` 未办结/未撤销（即尚在核查） |
| 刑拘在办 | `case_measure = 'DETENTION'` |
| 取保及监居 | `case_measure IN ('BAIL','RESIDENCE')` |

子模块页签内仍可按大类/小类/经办人继续筛选；初查页签默认按大类分组展示（行政初查 / 刑事初查：盗窃、电诈、接触性诈骗、故意伤害类、其他）。

## 4. 字段设计

### 4.1 `case_info` 扩展列（走 SchemaMigration.NEW_COLUMNS 幂等补列）

| 列名 | 类型 | 说明 |
|---|---|---|
| `case_measure` | VARCHAR(16) NULL | 强制措施：NONE/DETENTION/BAIL/RESIDENCE，默认 NULL 视为 NONE |
| `measure_date` | DATETIME NULL | 采取强制措施日期（刑拘日/取保决定日/监居决定日） |
| `detain_deadline` | DATETIME NULL | 强制措施期限届满日（刑拘=批捕期限，取保=12 个月，监居=6 个月，由措施日期推算可改） |
| `investigation_status` | VARCHAR(20) NULL | 侦查进度：PENDING_INITIAL/INVESTIGATING/PENDING_APPROVAL/INVESTIGATION_DONE |

> 快照兼容：`CaseSnapshot.info` 整体序列化 `CaseInfo`，加列后自动入快照；`CaseSnapshotService.compare` 的 diff 字段清单需补 `caseMeasure`、`investigationStatus`、`detainDeadline` 三行（否则变更明细缺这几项）。

### 4.2 新表 `case_plan`（侦查计划项——checklist）

```sql
CREATE TABLE IF NOT EXISTS case_plan (
    id          BIGINT       AUTO_INCREMENT PRIMARY KEY COMMENT '主键',
    case_id     BIGINT       NOT NULL COMMENT '案件 ID',
    content     VARCHAR(512) NOT NULL COMMENT '侦查计划内容（如：调取监控、询问证人、送检鉴定）',
    planned_at  DATETIME     DEFAULT NULL COMMENT '计划完成时限',
    status      VARCHAR(16)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING待完成/DONE已完成/CANCELLED已取消',
    done_at     DATETIME     DEFAULT NULL COMMENT '完成时间',
    done_note   VARCHAR(512) DEFAULT NULL COMMENT '完成情况说明',
    sort        INT          NOT NULL DEFAULT 0 COMMENT '排序',
    created_by  BIGINT       DEFAULT NULL COMMENT '录入人',
    created_at  DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at  DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '更新时间'
);
```

### 4.3 新表 `case_approval`（审批留痕）

```sql
CREATE TABLE IF NOT EXISTS case_approval (
    id            BIGINT       AUTO_INCREMENT PRIMARY KEY COMMENT '主键',
    case_id       BIGINT       NOT NULL COMMENT '案件 ID',
    approve_type  VARCHAR(20)  NOT NULL COMMENT 'INVESTIGATION_DONE 侦查终结审批 / MEASURE 强制措施变更确认',
    result        VARCHAR(16)  NOT NULL COMMENT 'APPROVED同意 / RETURNED退回补侦',
    comment       VARCHAR(512) DEFAULT NULL COMMENT '审批意见',
    approver_id   BIGINT       DEFAULT NULL COMMENT '审批人',
    approver_name VARCHAR(64)  DEFAULT NULL COMMENT '审批人姓名（冗余）',
    created_at    DATETIME     DEFAULT CURRENT_TIMESTAMP COMMENT '审批时间'
);
```

### 4.4 `case_suspect` 扩展（初查案件嫌疑人管理强化）

| 列名 | 类型 | 说明 |
|---|---|---|
| `is_detained` | TINYINT NULL | 是否已刑拘（初查案件掌握对象强制措施情况） |
| `detain_date` | DATETIME NULL | 刑拘日期 |

> 现有字段（姓名/性别/身份证号/联系电话/住址/备注）已满足"录入嫌疑人资料"，复用。

### 4.5 检索条件扩展（CaseQuery）

| 参数 | 说明 |
|---|---|
| `suspectName` | 按嫌疑人姓名模糊查（`case_id IN (SELECT case_id FROM case_suspect WHERE name LIKE)`） |
| `suspectIdCard` | 按身份证号精确/前缀查 |
| `module` | 盯办子模块：INITIAL（初查）/DETENTION（刑拘）/BAIL_RESIDENCE（取保监居），后端翻译成 measure + status 条件 |

## 5. 状态机流转

### 5.1 侦查生命周期状态机

```
                 ┌──────────────┐   开始侦查    ┌──────────────┐
   收案建案 ───▶ │  待初查        │ ───────────▶ │  侦查中        │
                 │ PENDING_INITIAL│              │ INVESTIGATING │
                 └──────────────┘ ◀─────────── └──────┬───────┘
                        ▲            退回补侦           │ 侦查工作完成
                        │                               ▼ 提请审批
                        │                        ┌──────────────┐  同意   ┌──────────────┐
                        │                        │  待审批        │ ──────▶ │  侦查终结      │
                        │                        │ PENDING_       │         │ INVESTIGATION│
                        │                        │  APPROVAL      │ ──拒绝─▶│  _DONE       │
                        └────────────────────────└──────────────┘         └──────────────┘
                                                                          并案对接：侦查终结后
                                                                          案件可走现有「办结」流程
```

### 5.2 流转规则表

| 当前状态 | 动作 | 目标状态 | 操作人 | 前置条件 |
|---|---|---|---|---|
| 待初查 | 开始侦查 | 侦查中 | 经办人/管理层 | 案件已指派（有主办） |
| 侦查中 | 提请审批 | 待审批 | 经办人 | 侦查计划至少 1 条已完成，或计划全部取消 |
| 待审批 | 同意 | 侦查终结 | 管理层（全权限） | 审批意见必填？否（可选），记录 case_approval |
| 待审批 | 退回补侦 | 侦查中 | 管理层 | 必须填审批意见 |
| 侦查终结 | —（并入现有办结） | — | 管理层 | `status` 置 DONE（现有 MANAGER_ONLY 规则） |
| 任意在办 | 采取/变更强制措施 | —（`case_measure` 变更） | 管理层 | 自动写 case_approval(MEASURE) |

### 5.3 权限矩阵

| 能力 | 普通民警 | 管理层（所长/副所长/法制员） |
|---|---|---|
| 看本人经办案件、录计划、勾完成 | ✓ | ✓ |
| 看全部案件、全部经办人 | ✗ | ✓ |
| 开始侦查 / 提请审批 | ✓（本人案件） | ✓ |
| 审批（同意/退回） | ✗ | ✓ |
| 强制措施登记/变更 | ✗ | ✓ |
| 嫌疑人增删改 | ✓（本人案件） | ✓ |

实现：审批与强制措施接口标 `@FullAccessOnly` 或走 `AuthContext.isFullAccess()` 业务校验（与现有办结规则一致）；计划/状态流转按「本人案件或全权限」校验。

## 6. 预警规则

预警统一由 `WatchService.alertOf(case, now)` 计算，产出分级标签，列表与看板消费；短信/企微通知复用已设计的 `notify_task` 通道（本期先落界面预警）。

| 编号 | 对象 | 触发条件 | 分级 | 展示 |
|---|---|---|---|---|
| W1 | 侦查计划 | 距 `planned_at` ≤ 3 天未完成 | 临期（黄） | 计划行黄色标记 + 案件行预警点 |
| W2 | 侦查计划 | 超过 `planned_at` 未完成 | 逾期（红） | 计划行红色 + 案件行红点 + 看板计数 |
| W3 | 强制措施期限 | 距 `detain_deadline` ≤ 7 天 | 临期（黄） | 案件行倒计时变黄 |
| W4 | 强制措施期限 | 距 `detain_deadline` ≤ 3 天 | 紧急（橙） | 倒计时变橙 + 看板计数 |
| W5 | 强制措施期限 | 超过 `detain_deadline` | 超期（红） | 倒计时红色 + 看板置顶 |
| W6 | 案件停滞 | 侦查中且 ≥ 7 天无任何计划完成/状态变化 | 停滞（灰） | 案件行「停滞 N 天」标记 |
| W7 | 审批滞留 | 待审批 ≥ 2 个工作日 | 滞留（橙） | 审批页签计数 + 管理层看板提醒 |
| W8 | 取保/监居 | 措施日期满 11 个月（取保）/ 5 个月（监居） | 提醒（蓝） | 案件行提示，预留续期办理 |

期限推算默认值（可在措施登记时修改）：刑拘 `detain_deadline = measure_date + 30 天`（提请批捕期限）；取保 `+12 个月`；监居 `+6 个月`。

## 7. 页面交互说明

### 7.1 导航与入口

侧栏新增「**案件盯办**」（全部角色可见），进入默认看板 + 三页签。

### 7.2 盯办看板（页顶，四卡片）

- **初查案件**：在手数 / 逾期未结 / 平均初查天数
- **刑拘在办**：在手数 / 临期（W3-W4） / 超期（W5）
- **取保及监居**：在手数 / 30 天内到期
- **待审批**：滞留数（W7）+ 一键跳转审批清单
- 每卡片点击跳对应页签并自动带上筛选条件（复用现有"点统计柱筛选"交互模式）

### 7.3 三页签列表（复用 cf-panel 体系，桌面端表格 / 手机端卡片）

列：案件编号 | 案件名称 | 类型（大类+小类标签） | 嫌疑人（数量+姓名摘要） | 经办人 | 侦查状态（彩色标签） | **进度条**（计划完成率 N/M + 百分比条） | **期限**（强制措施到期倒计时，按 W3-W5 变色） | 预警点 | 操作（详情/登记措施/提请审批）

- 初查页签：检索条件含 类型（大类级联）/ 小类 / **嫌疑人姓名 / 身份证号** / 关键字 / 经办人
- 刑拘、取保监居页签：检索条件含 经办人 / 期限状态（临期/超期）/ 进度状态
- 进度条三段色：绿（按期完成中）、黄（有临期计划）、红（有逾期计划或超期）

### 7.4 详情·侦查抽屉（在现有案件详情抽屉内新增「侦查盯办」面板，也可单独成页）

1. **侦查状态区**：当前状态标签 + 可用动作按钮（开始侦查/提请审批/审批[管理层]/退回补侦）
2. **强制措施卡**：措施类型、决定日期、期限届满日（倒计时）、登记/变更按钮（管理层）
3. **侦查计划 checklist**：新增（内容+计划时限）/ 勾选完成（填完成情况）/ 取消 / 逾期标色；底部实时进度条
4. **审批记录**：时间线展示同意/退回及意见
5. 嫌疑人面板（复用现有，扩展是否刑拘/刑拘日期）
6. 办理进度时间线（已有）

### 7.5 空态与提示

- 无强制措施期限的刑拘/取保案件 → 期限列提示「未登记期限」并给管理层入口
- 待审批被退回 → 状态回侦查中 + 审批意见置顶显示
- 全部操作沿用现有 message 提示与确认弹窗规范

## 8. 实现说明

### 8.1 后端

**改造点**
1. `CaseInfo` 实体 + 4 列；`SchemaMigration.NEW_COLUMNS` 登记；schema.sql 两份同步
2. `CaseSnapshotService.compare` diff 补 `caseMeasure/investigationStatus/detainDeadline`
3. `CaseQuery/CaseController.page` 加 `module/suspectName/suspectIdCard`
4. `DictHolder` 加 `INVESTIGATION_STATUS`（待初查/侦查中/待审批/侦查终结）、`CASE_MEASURE`（无/刑拘/取保候审/监视居住）

**新增**
- `CasePlan` 实体/Mapper + `PlanService`（CRUD 带 operation_log 留痕，undoable 白名单加 PLAN_ADD/PLAN_DONE/PLAN_CANCEL）
- `CaseApproval` 实体/Mapper + `ApprovalService`（写审批 + 驱动状态机）
- `WatchService`：子模块视图过滤、进度计算（done/total）、预警计算（W1-W8）、停滞天数
- `WatchController`：`GET /watch/cases`、`POST /cases/{id}/investigation-status`、`POST /cases/{id}/measure`、`POST /cases/{id}/approve`、`GET /watchboard`
- 状态机校验集中在 `ApprovalService.transition()`：非法流转抛 BizException，全部写操作带 before/after 快照

### 8.2 前端

- `views/WatchView.vue`：看板卡片 + el-tabs 三页签 + 列表 + 检索区
- `components/WatchDrawer.vue`：侦查面板（状态区/措施卡/计划 checklist/审批记录）
- `components/PlanChecklist.vue`：计划增删勾 + 进度条
- 进度条与预警点用现有色板（红 #c62a2a / 黄 #d98a0b / 橙 / 警蓝 #1b4a8c）
- 数据获取走 `watchApi`；经办人下拉复用现有 remote search

### 8.3 兼容与回滚

- 全部为增量变更（新列默认 NULL、新表独立），不动现有流程；盯办数据缺失时旧功能表现不变
- 回滚 = 回退代码 + `case_info` 新列置 NULL（或保留不用）；新表可整表保留不影响旧流程

### 8.4 已知边界（本期不做，列入后续）

- 多人协作编辑计划的冲突提示（乐观锁）——单民警场景出现概率低
- 预警的短信/企微主动推送——对接 `notify_task` 通道，属通知方案落地范畴
- 退侦/移送的检察院侧回执登记

## 9. 分期实施计划与验收口径

| 批次 | 内容 | 验收口径 |
