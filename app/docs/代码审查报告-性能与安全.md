# CaseFlow 代码审查报告 · 性能与安全

> 审查时间：2026-10-24
> 审查方式：静态代码走查 + 对运行中的服务做只读实测验证
> **约束：本次审查未修改任何代码、未改任何数据表与字段结构。所有修复建议均为代码级改动。**

---

## 一、结论摘要

| 级别 | 数量 | 说明 |
|---|---|---|
| 🔴 P0 高危（可立即被利用） | 3 | H2 控制台未授权、案件/嫌疑人越权读取、附件越权下载与删除 |
| 🟠 P1 高（数据泄露或可破坏数据） | 4 | 看板未按人收敛、CORS 任意源、登录无失败限流、SSE 全站广播 |
| 🟡 P2 中 | 4 | 上传无扩展名白名单、默认弱口令、token 出现在 URL、错误信息泄露账号是否存在 |
| ⚡ 性能（真实瓶颈） | 5 | 全表扫描无索引、待办列表 N+1、看板全表载入、期限提醒 N+1、快照双写 |

**最要紧的一句**：系统当前默认以 `dev` profile 启动，而这个 profile 把 **H2 数据库控制台开在了 `/api/console/`，且未做登录拦截**。任何人只要能在局域网打开浏览器，就能直连数据库、绕过全部权限读写数据。这是当前最严重的单点风险，且修复成本不到 5 分钟。

## 二、安全问题

### 🔴 S1. H2 数据库控制台未授权可访问（最高危）

**证据（实测）**

```
GET http://127.0.0.1:8080/api/console/    →  200，返回 H2 Console 页面
GET http://127.0.0.1:8080/api/console/login.do → 200
```

**成因（三处叠加）**

| 位置 | 内容 |
|---|---|
| `resources/application.yml:22` | `active: ${SPRING_PROFILES_ACTIVE:dev}` —— 未设环境变量时默认就是 dev |
| `resources/application-dev.yml` | `spring.h2.console.enabled: true`，`path: /console` |
| `config/WebConfig.java:50` | `excludePathPatterns(..., "/h2-console/**", "/console/**", ...)` —— 登录拦截器把控制台整个放行 |

**危害**：H2 控制台运行在同一个 JVM 内，默认连接串 `jdbc:h2:file:./data/h2/caseflow`、用户 `sa`、**空口令**，且控制台允许连接任意 JDBC URL。攻击者无需任何账号即可：读取全部案件/嫌疑人身份证/附件路径，或直接 `DELETE`/`UPDATE` 篡改办案数据。整个系统的鉴权体系在这一条面前完全失效。

**修复（代码级，不动表）**

1. `application-dev.yml` 里把 `spring.h2.console.enabled` 改为 `false`（本地确实要看库时用环境变量单独开）。
2. `WebConfig` 从 `excludePathPatterns` 中删掉 `/h2-console/**` 与 `/console/**`，让控制台至少要求登录。
3. 给 H2 设一个非空口令（仅改配置，不改表）。更彻底的做法是生产 profile 下彻底不引入 `spring-boot-starter-h2`（`mysql` profile 已不依赖它，只需确认打包时排除）。
4. 交付/生产一律显式 `SPRING_PROFILES_ACTIVE=mysql`，不要依赖默认值。

### 🔴 S2. 案件/嫌疑人/附件列表越权读取（IDOR）

**证据（实测，民警账号 `test1` 读取不属于自己的案件）**

```
民警可见案件数: 6 / 全库 28 件
目标案件 id=308（不在民警可见列表内）
  案件详情        : code=0  ❌ 越权成功
  嫌疑人含身份证手机: code=0  返回 1 条  ❌ 越权成功
  案件附件列表     : code=0  ❌ 越权成功
```

**成因**：列表接口做了数据范围收敛（`CaseService.page` 用 `buildWrapper` + `myVisibleCaseIds`），但**按 id 直取的接口完全没有校验**：

| 接口 | 代码位置 | 现状 |
|---|---|---|
| `GET /cases/{id}` | `controller/CaseController.java:121` → `CaseService.detail()` | 只判 `case != null`，无可见性校验 |
| `GET /cases/{id}/suspects` | `CaseController.java:213` → `SuspectService.listOf(caseId)` | 无任何校验 |
| `GET /files/case/{caseId}` | `FileController.java:64` | 无任何校验 |

**危害**：民警只要遍历 id（自增，成本极低）就能拿到全所所有案件的案情、**嫌疑人身份证号与手机号、住址**。这是典型的水平越权，也是涉个人信息泄露里最容易被追责的一类。

**修复（代码级）**

在 `CaseService` 加一个统一入口，所有按 id 直取的读接口先过它：

```java
// CaseService 内，复用已有唯一口径，不新增查询逻辑
public void requireVisible(Long caseId) {
    if (AuthContext.isFullAccess()) return;          // 管理层放行
    if (!myVisibleCaseIds().contains(caseId)) {
        throw new BizException(403, "无权查看该案件");
    }
}
```

调用点：`detail()`、`SuspectService.listOf()`、`FileService.filesOf()`、`TodoService.listOfCase()`、
`WatchService.plans()`、`LogService` 中按案件取的日志。`CaseCloseRequestService` 里已有 `requireVisible` 的正确写法，可直接复用同一风格。

> 注意：`CaseDeadlineService:349` 已经做了这件事，说明模式是对的，只是没有推广到其他接口。

### 🔴 S3. 附件越权下载 / 越权删除 / 无归属上传

**代码位置**：`controller/FileController.java`

```java
@GetMapping("/{id}/download")   public void download(@PathVariable Long id, ...)   // 只按 id 取，不校验案件归属
@DeleteMapping("/{id}")         public Result<Void> delete(@PathVariable Long id)  // 同上，且是写操作
@PostMapping("/upload")         public Result<CaseFileVO> upload(..., Long caseId) // 可往任意 caseId 挂附件
```

**危害**
- 下载：与 S2 同源，遍历 id 即可拖走任意案件的原始材料（案卷 PDF、照片）。
- **删除更严重**：任意登录用户可删掉他人案件的证据材料，且删除是物理删文件（`Files.deleteIfExists`），**不可恢复、不进回收站**。
- 上传：`caseId` 可为空 → 无限量孤儿文件写满磁盘（50MB × 无限次，无频率限制）。

**修复（代码级）**
1. `download` / `delete`：先查 `CaseFile`，再用其 `caseId` 走 S2 的 `requireVisible()`；`todoId` 非空时走待办所属案件的同一校验。
2. `delete`：只允许管理层或该案承办人；删除改为"软删除标记 + 定时清理"，避免误删不可逆。
3. `upload`：`caseId` 必填（有"先传材料再建案"的场景就改成"临时区 + 绑定"），并按用户限速。

### 🟠 S4. 盯办看板未按人收敛（数据越权 + 全表扫描）

**证据（实测）**

```
            管理层   民警（仅可见 6/28 件）
initialTotal   22   =   22
detentionTotal  4   =    4
bailTotal       2   =    2
```

**成因**：`WatchService.board()`（`service/WatchService.java:149`）整个方法没有接收当前用户、也没调 `myVisibleCaseIds()`，直接 `caseMapper.selectList(typeW)`（第 165 行）把**全库案件读进内存**再统计。

**危害**：民警能看到全所办案态势数字（多少人在押、多少取保），与"只能看自己案件"的口径冲突；同时这是全库扫描，数据量涨上去后接口会线性变慢。

**修复（代码级）**：方法签名加 `Set<Long> restrict`（非全权限时传 `myVisibleCaseIds()`），在 `typeW` 上追加 `in(CaseInfo::getId, restrict)`。已有现成范例：`CaseDeadlineService.active()` 第 47-49 行就是这么写的。

### 🟠 S5. CORS 允许任意源携带凭据

**代码位置**：`config/WebConfig.java:30-36`

```java
registry.addMapping("/**")
        .allowedOriginPatterns("*")
        .allowCredentials(true)
```

**危害**：任何外部网页都能对本系统发起携带 Cookie/凭据的跨域请求。虽然本项目鉴权走 `X-Token` 头（跨域页面拿不到 localStorage），实际利用难度较高，但一旦后续有人加了 Cookie 会话或把 token 放进 URL，这里立刻变成突破口。

**修复**：改成从配置读白名单（`caseflow.cors.allowed-origins`），生产环境只填内网地址；`allowCredentials` 仅在确有必要时开。

---

### 🟠 S6. 登录无失败限流 / 无锁定 + 账号枚举

**代码位置**：`service/AuthService.java:55-80`

- 密码错误只抛 `BizException(401, "密码错误")`，**没有失败计数、没有验证码、没有锁定、没有延迟**。BCrypt 只增加了单次尝试成本，挡不住持续撞库。
- 提示语区分了「账号不存在」与「密码错误」（第 61 行 vs 76 行），可用来批量枚举有效账号。
- 口令下限只有 6 位（`UserService:177`），且默认管理员是 `boss / admin123`。

**修复（代码级，无需改表）**：在 `AuthService` 内用内存 Map（`ConcurrentHashMap<String, FailCounter>`）做"同账号 5 次失败锁 10 分钟 + 同 IP 每分钟 20 次"，锁定状态只在内存、重启即清，不涉及任何表结构。同时把两种错误提示统一为「用户名或密码不正确」，并强制首次登录修改默认口令。

---

### 🟠 S7. SSE 全站广播 + token 出现在 URL

**代码位置**：`support/SseHub.java:37`、`controller/EventController.java:33`、`security/LoginInterceptor.java:36`

- `broadcast()` 把每条事件发给**所有在线连接**，事件体里带案件名/操作内容 → 任何登录用户都能收到别人的案件动态。
- `EventSource` 无法带头，所以 token 走 `?token=`，会被写进浏览器历史、反向代理 access log、Referer。

**修复（代码级）**：`register()` 时把 `CurrentUser` 一起存下，`broadcast` 按事件里的 `caseId` 过滤（管理层全收）；token 改为一次性的短期 `sseTicket`（登录后换取，30 秒有效、用后即焚），避免长令牌进日志。

---

### 🟡 S8. 案件材料上传无扩展名白名单

`FileService.upload()`（第 143-145 行）只在 `todoId != null` 时调 `checkEvidence()` 做白名单校验；普通案件材料传什么扩展名都收（含 `.exe` / `.html` / `.jsp`）。

目前下载统一是 `Content-Disposition: attachment` + `application/octet-stream`，所以不会被浏览器当页面执行，风险可控。但建议把白名单校验提到方法入口，对所有上传统一生效（一份代码，两条路径都覆盖）。

## 三、性能问题

### ⚡ P1. 全库 22 张表只有 1 个二级索引（性能问题的总根源）

`sql/schema.sql` 中只有一处 `KEY idx_case_node (case_id)`，其余全部只有主键。

高频查询裸奔（全部走全表扫描）：

| 查询 | 位置 | 没有索引的列 |
|---|---|---|
| 待办按案件取 | `TodoService.listOfCase` | `case_todo.case_id` |
| 佐证材料计数 | `TodoService.toVO:1197` | `case_file.todo_id` |
| 嫌疑人按案件取 | `SuspectService.listOf` | `case_suspect.case_id` |
| 通知未读 | `NotificationService.unreadForMe` | `case_notification(user_id, read_at)` |
| 承办人判定 | `CaseScopeService.myVisibleCaseIds` | `case_assignee(employee_id, status)` |
| 领导意见按案件 | `OpinionService` | `case_leader_opinion.case_id` |
| 日志按对象 | `LogService` / 撤回 | `operation_log(target_type, target_id)` |

**影响**：现在是几十件案件，感知不到；几百件、几千条待办后，上述每个接口都会退化成全表扫描，且是在最热的列表页路径上。

**建议（⚠️ 会动 schema，需你确认后我再执行，本次未做）**：按上表列各补一个联合索引即可，不改任何字段、不改表语义。这是投入产出比最高的一项优化。

### ⚡ P2. 待办列表 N+1：每行最多 4 次查库

**代码位置**：`service/TodoService.java:1197` 起（`toVO`）

```java
vo.setFeedbackCount(feedbackCount != null ? feedbackCount
        : feedbackMapper.selectCount(...).intValue());   // ① 每条待办 1 次 COUNT
vo.setDoneByName(userName(t.getDoneBy()));               // ② 1 次 selectById
vo.setCreatedByName(userName(t.getCreatedBy()));         // ③ 又是 1 次
int cnt = fileService.countOfTodo(t.getId());            // ④ 1 次 COUNT
```

`userName()`（第 1206 行）内部是 `userMapper.selectById(id)`，同一页面里反复查同一个人。

**量级**：一个民警 50 条待办 → 最坏 **200 次数据库往返**；管理层待办总览同理。这是当前最具体的性能瓶颈。

**修复（代码级）**：`toVO` 增加两个入参——预聚合的 `Map<Long,Integer> feedbackCounts` 与 `Map<Long,Integer> evidenceCounts`，列表层用一次 `GROUP BY todo_id` 批量取；`userName` 换成传入 `Map<Long,String>`（`employeeMap()` 已有同类做法）。`CaseService.page` 里对嫌疑人做批量预取（`suspectsOf`）就是标准样板，照抄即可。

---

### ⚡ P3. 待办总览再次 N+1

**代码位置**：`service/TodoService.java:325`

```java
for (CaseTodo t : all) {
    if (isDone && fileService.countOfTodo(t.getId()) <= 0) { doneNoEvidence++; }
}
```

一次 `selectList` 拉全部待办，然后**对每一条已完成待办单独发一次 COUNT**。1000 条已完成 → 1000 次查询。

**修复**：一次 `SELECT todo_id, COUNT(*) FROM case_file WHERE todo_id IS NOT NULL GROUP BY todo_id`，转成 Set 后内存判断。

---

### ⚡ P4. 期限提醒逐案查库

**代码位置**：`service/CaseDeadlineService.java:55`

```java
for (CaseInfo c : cases.selectList(q)) {
    for (Item item : view(c.getId()).getItems())   // 每个案件 1 次 selectList
```

N 个在办案件 → N 次查询（外加每个案件的节点计算）。`active()` 是「到期提醒」页的主接口。

**修复**：先收集所有 caseId，一次 `in(caseId, ids)` 把节点记录全拉出来按 caseId 分组，再在内存里跑同样的节点计算逻辑——`view()` 的算法本身不用改。

---

### ⚡ P5. 看板全表载入 + 员工表每请求全量加载

- `WatchService.board()` 第 165 行 `caseMapper.selectList(typeW)`：无条件全表读入内存，再在 Java 里做 5 层 `stream().filter()` 分桶（数据越权见 S4）。案件量上千后，单次请求要序列化+过滤上千行。
  最省事的改法是**把分桶条件下推到 SQL**（`status not in (...)`、`case_measure in (...)`），用 4~5 条 `GROUP BY` 计数替代全量载入。
- `EmployeeService.employeeMap()` 每次调用都 `selectList(null)` 拉全表；`CaseService.page()` 里连着调了 `employeeMap()` + `pathNameMap()` 两次。员工表不大（几十到几百行），但它在**每个列表请求**上都发生。建议加一层短 TTL（如 30 秒）的进程内缓存，改动只在一个方法内。

---

### ⚡ P6. 每次写操作捕获两次全案快照

`CaseSnapshotService.capture(caseId)` 会把这个案件的案件主体、嫌疑人、待办、计划、意见全部查出来序列化成 JSON，作为 `operation_log` 的 before/after 存库。

调用点（`grep capture(`）有 10+ 处，且**一次写操作通常前后各捕获一次**（如 `CaseService:1119` + `1126`）。大案件（几十条待办 + 多嫌疑人）单次写会产生两次全量查询 + 两份大 JSON 落库。

**建议（代码级）**：after 快照可延迟到日志提交前统一生成；或对"纯字段更新"类操作只存变更字段的 diff，而不是整案 JSON。改动集中在 `CaseSnapshotService`，不影响其他逻辑。

---

### ⚡ P7. 前端主包 1.1 MB

```
index-BPphQxfU.js   1107 KB   ← 路由已懒加载，但公共依赖全在这
chart-DdfclN84.js    572 KB
CaseDetailDrawer.js  129 KB
```

路由级懒加载做得对，问题是主 chunk 把 Element Plus 全量打了进去。内网带宽下勉强可用，但首屏在旧机器上会明显卡。

**建议**：Element Plus 改为按需引入（`unplugin-vue-components` + `ElementPlusResolver`），可把主包降 40% 左右；`chart` 已经是独立 chunk，保持现状即可。

## 四、做得好的地方（不需要动）

避免只列问题，这些是审查中确认没问题的：

- **SQL 注入**：全项目 0 个 XML mapper，`${}` 只出现在配置读取（`@Value`）和 `application.yml` 的 JDBC 连接串里，**没有任何一处把前端入参拼进 SQL**。`WatchService` 里还专门留了注释说明"不拼字符串，走 Lambda 条件"。
- **密码存储**：统一 BCrypt，且历史明文在登录成功时自动升级（`PasswordService`），方向正确。
- **分页与上限**：`CaseService.page` 的 `size` 硬顶 200；`CaseService.page` 对嫌疑人做了批量预取（`suspectsOf`），没有落进 N+1 的坑；`NotificationService.listForMe` 有 `LIMIT 200`。
- **令牌管理**：`TokenStore` 有单账号会话上限（5）和过期清理，停用账号会 `removeAll` 立即踢下线——比单纯查 `status` 位更可靠。
- **上传文件名**：存储名是 `时间戳_UUID.扩展名`，原始名只存库用于展示/下载，**不存在路径穿越**。
- **下载响应头**：`Content-Disposition: attachment` + `octet-stream`，上传的 HTML 不会被浏览器当页面执行。
- **日志埋点单点化**：`LogService.log` 是唯一汇聚点，撤回/通知/SSE 都从这一处派生，没有散落的重复实现。

## 五、修复优先级建议

| 顺序 | 事项 | 工作量 | 是否动 schema |
|---|---|---|---|
| 1 | 关掉 H2 控制台 + 把它纳入登录拦截（S1） | 5 分钟 | 否 |
| 2 | 加 `requireVisible()` 并挂到 detail / suspects / files / todo（S2、S3） | 1~2 小时 | 否 |
| 3 | 看板按人收敛（S4，与 S2 同一个 `myVisibleCaseIds`） | 30 分钟 | 否 |
| 4 | 登录失败限流 + 统一错误提示（S6） | 1 小时 | 否 |
| 5 | 待办 / 总览 / 期限提醒三处 N+1 批量化（P2~P4） | 半天 | 否 |
| 6 | 补 7 个二级索引（P1，性能总根源） | 30 分钟 | **是（仅加索引）** |
