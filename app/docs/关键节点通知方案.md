# 案件关键节点 · 点对点通知方案

> 目标：案件流转到关键节点时，把「案件编号 / 名称 / 进度 / 期限」等要素**点对点**推到主办、协办及其上级的**手机**上，做到该办的人一定知道、办完的人不再被打扰。
> 适用现状：CaseFlow 现有 `case_info` / `case_assignee` / `org_employee` / `operation_log` 四张表已具备事件源、收件人、判定规则三块地基，无需重构。

---

## 一、先把「关键节点」定义清楚

**这是最容易做错的一步。** 若把每个操作都推一遍，两周内所有人就会把通知关掉。原则：

> 只有「改变了责任归属」或「时间进入风险区」才算关键节点。

### 1.1 动作型节点（事件驱动，秒级触发）

| 节点 | 触发时机 | 为什么必须通知 |
|---|---|---|
| 新案待指派超时 | 建案后 N 分钟仍未指派 | 案件卡在入口，责任真空 |
| **指派 / 改派** | `assign()` 成功 | 责任归属发生变化，**核心节点** |
| 期限变更 | `save()` 改了 `deadline` | 办了 8 天突然提前，不通知必出事 |
| 办结 / 撤销 | `changeStatus()` | 协办停止被催办；撤销后要立刻停催 |
| 撤回（Ctrl+Z） | `UNDO` 且影响案件 | 上一条通知可能已失效，需发更正 |
| 久拖未动 | 进入处理中后 N 天无任何写操作 | 静默逾期比明面逾期更危险 |

**现有 `operation_log` 已经是天然的完整事件源**——`CREATE / UPDATE / ASSIGN / STATUS / DELETE / UNDO` 全都埋好了点，含 `snapshot_before/after`。通知模块不必新造埋点，直接在写日志的地方顺带投递事件即可，成本极低。

### 1.2 时间型节点（定时扫描，宜每日 08:30 + 每小时补扫）

沿用 `DictHolder.dueLevel()` 已有口径，扩成可配置的 T 值：

| 节点 | 判定 | 强度 |
|---|---|---|
| 临期 | `deadline` 距今 3 天 | 低 |
| 临期 | 距今 1 天 | 中 |
| 当天到期 | 到期日当天 08:30 | 中 |
| 逾期 | 已过 `deadline` | 高 |
| 严重逾期 | 逾期 ≥ 3 天 | 最高 |

对应前端现有的「逾期整行淡红 / 临期淡黄」两档，正好可以再加「临期 1 天」一档。

## 二、点对点：怎么准确找到「谁」的手机

### 2.1 收件人从案件反查，不从账号反查

```
case_info.id
  → case_assignee (case_id = ?, status='ACTIVE')
      → assign_role = 'OWNER'  ⇒ 主办（必收、需办）
      → assign_role = 'MEMBER' ⇒ 协办（知会、看简版）
  → org_employee.id → phone / 上级(parent_id 上溯)
```

**关键判断：收件人必须走 `org_employee`，不能走 `sys_user`。**
一线办案人员绝大多数没有系统账号，但每个人都在员工图谱里、都有手机号——只用 `sys_user` 会漏掉大部分真正需要通知的人。

### 2.2 三档收件范围

| 角色 | 何时收 | 内容详略 |
|---|---|---|
| 主办 OWNER | 该案全部节点 | 完整版 |
| 协办 MEMBER | 指派 / 改期 / 办结 / 逾期 | 精简版，不含催办语气 |
| 上级（`parent_id` 上溯 1~2 层） | **仅**逾期 / 待指派超时 / 久拖未动 | 点名主办 + 逾期天数 |

上级「默认只在出事时才被叫醒」是这套设计的关键——否则队长每天收几十条与自己无关的通知，很快就不看了。

### 2.3 一个容易漏的坑：**取消未发出的通知**

案件办结后还在推「临期提醒」、原主办改派后还在收该案短信——这类错误对使用者信任的破坏极大。因此每次**办结 / 撤销 / 改派**时必须执行：

```sql
UPDATE notify_task SET status='CANCELLED'
WHERE case_id = ? AND status IN ('PENDING','RETRY')
  AND (receiver_employee_id = ?  -- 改派时只撤销原承办人
       OR ? IS NULL)            -- 办结/撤销时撤销该案全部待发
```

## 三、渠道选型

### 3.1 渠道能力对比

| 渠道 | 是否真点对点 | 成本 | 到达率 | 落地难度 |
|---|---|---|---|---|
| 站内消息（系统内红点） | ✅ | 0 | 需登录才看到 | 低 |
| **企业微信自建应用消息** | ✅ **推荐主力** | 0 | 高（有消息推送） | 中 |
| 短信 | ✅ | 按条约 0.03~0.05 元 | 最高 | 中（需报备模板） |
| 语音外呼 | ✅ | 约 0.1 元/次 | 最高（强制提醒） | 高 |
| 企微/钉钉**群机器人** | ❌ **伪点对点** | 0 | 中 | 低 |

**必须避开的错误做法：用群机器人 webhook 代替点对点。**
群机器人只能发到群里、无法指定个人、离职后还能看到历史消息。要实现「点对点」必须走**自建应用**，用 `touser={userid}` 指定收件人：

```
POST https://qyapi.weixin.qq.com/cgi-bin/message/send?access_token=xxx
{
  "touser": "zhangsan|lisi",          // 企微 userid，非手机号
  "msgtype": "textcard",
  "agentid": 1000002,
  "textcard": {
    "title": "【案件指派】2026-XX 涉嫌电信诈骗案",
    "description": "<div class=\"gray\">CA-20260929-001</div><div>当前进度：已指派（您是主办）</div><div>截止期限：10-08 18:00 · 剩 8 天</div>",
    "url": "http://your-host/#/cases/1024",
    "btntxt": "查看案件详情"
  }
}
```

若单位已有 OA / 短信平台 / 统一消息网关，**优先对接现有平台**，比自建短信通道省掉签名与模板报备流程。

### 3.2 最终分级矩阵

| 节点 | 主办 | 协办 | 上级 | 渠道 |
|---|---|---|---|---|
| 待指派超时 | — | — | 管理员 | 站内 + 企微 |
| 指派 / 改派 | ✅ 完整 | ✅ 精简 | — | 站内 + 企微 |
| 期限变更 | ✅ | ✅ | — | 站内 + 企微 |
| 临期 T-3 / T-1 | ✅ | 抄送 | — | 站内 + 企微 |
| 当天到期 | ✅ | — | — | 企微 + **短信** |
| 逾期 T+0 | ✅ | — | ✅ 知会 | 短信（+ 企微） |
| 逾期 ≥ T+3 | ✅ | — | ✅ | 短信 + **语音外呼** |
| 办结 / 撤销 | ✅ | ✅ | — | 站内 + 企微 |

一句话概括：**站内全程兜底，企微主推，短信只在进入风险区后动用，语音只留给严重逾期。**

## 四、消息内容

### 4.1 企微完整版（主办）

```
【案件指派】2026-XX 涉嫌电信诈骗案
特急 · 刑事案件 · 09-29 09:12
案件编号：CA-20260929-001
当前进度：已指派（您是主办）
截止期限：10-08 18:00 · 剩 8 天
协作人员：协办 1 人：陈组员
指派要求：3 日内完成初查并反馈
[ 查看案件详情 ]
```

### 4.2 短信精简版（**建议锁死在 70 字内**）

```
【案件指派】CA-20260929-001 2026-XX涉嫌电信诈骗案已指派您为主办，期限10-08 18:00，请及时办理。
```

要点：
- `【案件指派】` 同时充当**签名**与**模板标识**，报备通过后不可随意改动；
- 不出现超链接（长链接会大幅提高被拦截概率，且短信内链接容易被当成诈骗）；
- **正文只放编号 + 名称简称 + 期限**，敏感案情细节一律不放，详细内容引导到系统内查看（登录后可见，天然有权限控制）。

### 4.3 逾期抄送上级版

```
【案件逾期】CA-20260929-001 2026-XX涉嫌电信诈骗案已逾期3天，主办张组长，请督促办理。
```

### 4.4 聚合，避免通知风暴

同一收件人在 10 分钟内收到同类通知 ≥ 3 条时，**合并成一条摘要**：

```
【到期提醒】您名下今日有 5 个案件即将到期，其中 2 个已逾期。请进入系统查看。
```

批量导入案件、一次性指派多名协办、每日定时扫描这三个场景最容易触发风暴，聚合逻辑必须在一期就做。

## 五、数据模型

新增两张表，登记进 `sql/schema.sql`（兼容 H2 / MySQL）；已有库升级走 `bootstrap/SchemaMigration` 的 `NEW_COLUMNS` 约定。

### 5.1 `notify_channel` 员工渠道绑定

```sql
CREATE TABLE IF NOT EXISTS notify_channel (
    id           BIGINT       AUTO_INCREMENT PRIMARY KEY,
    employee_id  BIGINT       NOT NULL COMMENT '员工图谱 ID',
    channel      VARCHAR(16)  NOT NULL COMMENT 'INAPP/WECOM/SMS/VOICE',
    address      VARCHAR(128) NOT NULL COMMENT '手机号或企微 userid',
    verified     TINYINT      NOT NULL DEFAULT 1 COMMENT '1已确认 0待确认',
    status       TINYINT      NOT NULL DEFAULT 1 COMMENT '1可用 0停用（离职/换号）',
    bound_at     DATETIME     DEFAULT CURRENT_TIMESTAMP
);
```

`org_employee` 已有 `phone`，可作初始值灌入；企微 `userid` 建议用「工号」对齐（导入 Excel 时已有工号，可在企微后台按工号建号，避免维护两套 ID）。

### 5.2 `notify_task` 待发任务 + 投递留痕（一张表兼顾）

```sql
CREATE TABLE IF NOT EXISTS notify_task (
    id               BIGINT       AUTO_INCREMENT PRIMARY KEY,
    biz_key          VARCHAR(160) NOT NULL UNIQUE COMMENT '幂等键，见下',
    case_id          BIGINT       DEFAULT NULL,
    node_code        VARCHAR(32)  NOT NULL COMMENT 'ASSIGN/DUE_T3/DUE_T1/DUE_TODAY/OVERDUE/...',
    receiver_id      BIGINT       NOT NULL COMMENT '收件人 employee_id',
    receiver_role    VARCHAR(16)  DEFAULT NULL COMMENT 'OWNER/MEMBER/PARENT/ADMIN',
    channel          VARCHAR(16)  NOT NULL,
    title            VARCHAR(128) DEFAULT NULL,
    content          VARCHAR(1024) DEFAULT NULL,
    status           VARCHAR(16)  NOT NULL DEFAULT 'PENDING' COMMENT 'PENDING/SENT/FAILED/DEAD/CANCELLED/SKIPPED',
    retry_count      INT          NOT NULL DEFAULT 0,
    next_retry_at    DATETIME     DEFAULT NULL,
    provider_msg_id  VARCHAR(128) DEFAULT NULL COMMENT '运营商/企微回执 ID',
    sent_at          DATETIME     DEFAULT NULL,
    delivered_at     DATETIME     DEFAULT NULL COMMENT '送达回执时间',
    error_msg        VARCHAR(512) DEFAULT NULL,
    created_at       DATETIME     DEFAULT CURRENT_TIMESTAMP
);
```

**幂等键是整张表的核心**，没有它就会出现「同一天发三条提醒」：

```
biz_key = caseId : nodeCode : receiverId : channel : cycle
cycle   = 动作型节点填事件发生时间戳（同一件事可重发，但不会重复发）
          时间型节点填日期 YYYYMMDD（同一天同一节点只发一次）
```

`UNIQUE` 索引 + `INSERT ... ON DUPLICATE KEY IGNORE`（或吞掉唯一键冲突）= 天然幂等，不需要额外加锁。

## 六、在本项目里的落点

| 环节 | 位置 | 做法 |
|---|---|---|
| 事件投递 | `service/CaseService` 各写方法 | 在 `logService.log(...)` 之后调用 `notifyService.emit(nodeCode, caseId, ...)` |
| 事件解耦 | 新增 `support/NotifyEvent` | 用 Spring `ApplicationEventPublisher`，业务代码不感知通知实现 |
| 任务落库 | 新增 `service/NotifyService` | **与业务同一个事务**，只写 `notify_task`，绝不在这里发 HTTP |
| 定时投递 | 新增 `job/NotifyDispatchJob` | `@Scheduled(fixedDelay=10s)` 扫 `PENDING/RETRY`，逐条调渠道 |
| 期限扫描 | 新增 `job/DueScanJob` | 每日 08:30 全量扫 + 每小时补扫，复用 `DictHolder.dueLevel()` |
| 渠道适配 | 新增 `notify/NotifySender` 接口 | `InAppSender` / `WecomSender` / `SmsSender` / `VoiceSender`，`Map<String, NotifySender>` 按 `channel` 分发 |
| 发送记录 | 复用 `/api/logs` 思路 | 新增 `GET /api/notify/tasks` 供管理员查「谁收到了什么、成功没有」 |
| 前端 | 顶栏加消息铃铛 | 站内消息中心 + 未读红点；`EmployeeTree.vue` 员工详情里显示渠道绑定状态 |
| 开关 | `notify_channel` + 可选 `notify_pref` | 允许个人关闭非逾期类通知、设置静默时段 |

**注意**：`@Scheduled` 需要新增 `@EnableScheduling`，当前项目还没有任何定时任务，属于新增能力。

## 七、四个必须做的保障

### 7.1 异步投递（最重要）

```
❌ 错误：业务事务里同步调企微 HTTP
   → 企微抖动 3 秒 = 用户点「指派」卡 3 秒；企微 500 = 指派操作回滚
✅ 正确：事务内只 INSERT notify_task，异步进程投递
```

这是「Outbox 模式」。它同时解决了：业务响应速度、发送失败重试、以及「操作成功了但消息没发出去」这种最难排查的问题。

### 7.2 重试与退避

```
PENDING → 投递 → SENT
              ↘ 失败 → retry_count++ → next_retry_at = now + 2^n 分钟（1/2/4/8/16）
                        retry_count >= 5 → DEAD（进管理后台人工处理）
```

### 7.3 静默时段与频控

- 21:00 – 次日 08:00 **不发送**非逾期类短信/语音（站内可照常落库，上班后补发）；
- 单个收件人 / 单日短信上限（建议 ≤ 10 条），超限转站内；
- 逾期类不受静默限制，但同一案件逾期短信每日最多 1 条。

### 7.4 留痕（办案系统的合规刚需）

每条通知必须可查：**谁 → 什么时候 → 哪个渠道 → 什么内容 → 成功/失败/送达**。
`notify_task` 的 `status / sent_at / delivered_at / provider_msg_id / error_msg` 就是留痕依据，不可省略、不可只写内存日志。

## 八、落地节奏

| 期 | 范围 | 价值 |
|---|---|---|
| **一期** | 站内消息中心 + 企微自建应用；动作型节点全量 + 临期/逾期扫描；幂等、聚合、取消机制 | 覆盖 80% 需求，**零短信成本**，一至两周可上线 |
| **二期** | 接入短信（先只用于当天到期 + 逾期）、静默时段、个人订阅偏好 | 补上「不登录也能收到」的短板 |
| **三期** | 语音外呼（仅严重逾期）、送达回执看板、通知效果统计（如逾期案件平均响应时长） | 管理闭环 |

## 九、上线前必须确认的外部事项

这几件事会直接卡住进度，**开工前就要推动**：

1. **企业微信**：需企业管理员在后台创建自建应用，提供 `corpid` / `secret` / `agentid`；服务器公网 IP 需加入「可信 IP」白名单；员工 `userid` 与工号的对应关系要确认。
2. **短信**：需向服务商报备**签名**与**模板**，审核通常 1–3 个工作日，模板内容一旦通过不能随意改；注意运营商对含链接、含「案件」「诈骗」等敏感词的模板有额外审核。
3. **语音外呼**：需语音网关资质，同样要报备 TTS 模板。
4. **合规与隐私**：手机号属个人信息，需在员工知情范围内使用；短信正文避免出现敏感案情细节，详细内容一律引导至系统内（登录 + 权限控制）。
5. **成本**：短信按条计费、量级在每月百元级（视案件量与通知节点数），语音更高——所以分级策略不只是体验问题，也是成本问题。

---

## 十、一句话总结

> 把「关键节点」定成动作型 + 时间型两类事件，收件人从案件的现役承办人反查到员工手机号，通知**先落一张任务表再异步投递**，渠道按风险分三档（站内 → 企微 → 短信/语音），并且记得在办结、撤销、改派时**撤销尚未发出的通知**。
