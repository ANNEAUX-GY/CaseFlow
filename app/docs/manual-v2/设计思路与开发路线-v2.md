## 第 1 章 系统概览与技术选型

### 1.1 定位

CaseFlow 是一套面向基层所队的**案件指派与盯办系统**，覆盖「收案件 → 指派（主办+协办）→ 盯到期 → 办结」全链路，强调**操作可追溯、误操作可撤回**。

### 1.2 技术栈

| 层 | 技术 | 版本 | 选型理由 |
|---|---|---|---|
| 后端框架 | Spring Boot | 2.7 | 稳定、社区成熟、内网部署简单 |
| JDK | Java | 8 | 目标运行环境统一在 JDK8 |
| ORM | MyBatis-Plus | — | 单表 CRUD 免写 SQL，复杂统计仍可手写 |
| 数据库（开发） | H2 | — | 文件库，零安装，便于单机开发 |
| 数据库（生产） | MySQL | 8 | 内网正式部署 |
| 前端 | Vue 3 + Element Plus | — | 组合式 API + 成熟组件库 |
| 状态管理 | Pinia | — | 跨组件计数/状态集中管理 |
| 图表 | ECharts | 5.5.1 | 看板与趋势图 |
| 实时 | SSE（Server-Sent Events） | — | 单向广播足够，比 WebSocket 轻 |

### 1.3 部署形态

**纯内网、纯桌面端应用**（2026-10-08 起确定不做移动端，全部移动端代码已删）。

- 前端构建产物 `base='/api/'`，由 Maven 打包进后端 `static/`。
- 浏览器访问 `http://<内网IP>:8080/api/`。
- 打包必须 `clean package`，且先杀掉占用 8080 的进程。

## 第 2 章 总体架构：一次写操作如何流遍全站

系统最关键的一条设计主线是**「所有写操作汇聚到一个埋点入口」**：

```
   用户操作（建案/指派/流转/登记时限…）
              │
              ▼
      Controller（鉴权 + 参数校验）
              │
              ▼
      Service（业务逻辑 + 事务）
              │
              ├─────────────► 写业务表（case_info / case_todo / …）
              │
              ▼
      LogService.log(...)   ◄──── 全量埋点的唯一汇聚点
              │
              ├──► 写 operation_log（含 before/after 双快照）→ 支持撤回
              │
              └──► SseHub.broadcast(...) → 广播给所有在线浏览器
                          │
                          ▼
                前端 store/events.js 接收 → 局部或整页刷新
```

**为什么这样设计**：

- **埋点只写一处** —— 要新增/修改埋点，只动 `LogService` 一个类，不会漏埋、不会重复。
- **追溯与实时天然一致** —— 因为日志与广播是同一个入口发出的，能记进日志的操作必然也能触发前端刷新，两者不会打架。
- **撤回能统一** —— 因为每条写操作都带了改前/改后快照，撤回逻辑可以简化为「把 before 写回去」。

## 第 3 章 领域模型：案件数据的骨架

### 3.1 核心表

| 表 | 职责 | 关键字段 |
|---|---|---|
| `case_info` | 案件主表 | `case_type`、`flow_stage`、`case_measure`、`measure_date`、`accept_time`、`status`、`focus` |
| `case_assignee` | 承办关系 | `case_id`、`employee_id`、`status`(ACTIVE) |
| `case_todo` | 案件待办 | `opinion_id`(派生来源)、`flow_stage`、`parent_id`(两级子任务) |
| `case_leader_opinion` | 领导意见 | 待办的唯一载体 |
| `case_deadline_state` | 期限状态 | `detention_term`、`paused_at`、各类节点登记时间 |
| `case_time_node` | 重要时间节点 | 节点类型 + 日期 + 提前提醒天数 |
| `case_suspect` | 嫌疑人 | 姓名/性别/身份证/电话 |
| `case_file` | 佐证材料 | 关联文件 |
| `org_employee` | 员工档案 | `police_group`(办案组别，权威来源) |
| `sys_user` | 登录账号 | `role`、`audit_status` |
| `operation_log` | 操作日志 | before/after 双快照 JSON |

### 3.2 案件类型的存储与查询口径

- **存储码**：`case_info.case_type` ∈ `CRIMINAL`（刑事）/ `ADMINISTRATIVE`（行政）/ `PRELIMINARY`（未立案）。
- **查询口径**：前端「其他」= 非刑事且非行政（含空值）。它是**查询口径**，不是第四种存储码。

```java
// 后端「其他」的查询：NOT IN (CRIMINAL, ADMINISTRATIVE) OR IS NULL
else if ("OTHER".equals(caseType))
    q.and(w -> w.notIn(CaseInfo::getCaseType, "CRIMINAL", "ADMINISTRATIVE")
                .or().isNull(CaseInfo::getCaseType));
```

### 3.3 两套并存的「状态线」（重要）

案件上有**两条独立演进的状态线**，互不干扰：

| 字段 | 管什么 | 状态机 |
|---|---|---|
| `flow_stage` | 走到哪个办理阶段、进度多少 | **办案阶段流程**（初查→刑拘→取保→终结） |
| `investigation_status` | 侦查终结要不要领导审批 | **盯办审批状态机**（PENDING_INITIAL → INVESTIGATING → PENDING_APPROVAL → INVESTIGATION_DONE） |

**设计裁决**：办案阶段流转**不改动** `investigation_status`；审批流转也**不改动** `flow_stage`。两条线各自独立，避免了「改一处连带另一处」的耦合。

## 第 4 章 核心设计一：办案阶段由「待办驱动」

### 4.1 四个阶段

| 常量 | 中文 | 含义 |
|---|---|---|
| `INITIAL` | 初查 | 接收材料 → 立案 → 侦查 → 判断是否符合刑拘条件 |
| `DETAIN` | 刑拘在办 | 刑事拘留期间办理 |
| `BAIL` | 取保及监居 | 取保候审 / 监视居住执行 |
| `CLOSED` | 已终结 | 案件办理完毕 |

`flow_stage` 为 NULL 的存量案件**一律按 INITIAL 归位**（`stageLabel` 与 `FlowService.stageOf` 口径一致）。

### 4.2 关键取舍：删掉「环节 → 标准任务」三层模板

**旧版本**维护了三层模板（`STEP_*` + `STEP_TASKS`），建案时自动铺 13 项标准任务。**问题**：

> 它与民警日常用的「案件待办」是**两套并行任务清单**——同一个案子要在一处勾「接收材料/立案/侦查」，又要在另一处勾领导交代的事，两处数字永远对不上，用户明确要求删掉。

**现版本**（2026-10-12 定稿）：

> **阶段任务 = 案件待办**。只有一份清单，彻底消除双清单问题。

### 4.3 进度怎么算（不落库，实时算）

```java
阶段进度 = 该阶段的待办已完成数 / 该阶段的待办总数
```

**判据落在 `case_todo.flow_stage`**：领导提意见派生的待办会自动记下当时所处阶段。流转后新阶段的待办从 0 起算，**进度天然归零，不需要任何"重置"动作**。

`CLOSED` 阶段进度恒 100%（避免「办结了还显示 60%」）。

### 4.4 流转：不自动跳，领导确认

**流转出口**由 `CaseFlowTemplate.transitionsOf(caseType, stage)` 声明，纯数据：

```java
if (STAGE_INITIAL.equals(stage)) {
    if (ADMIN_TYPES.contains(caseType)) out.add({"PUNISH", CLOSED});   // 行政
    else                                 out.add({"DETAIN", DETAIN});   // 刑事唯一出口
} else if (STAGE_DETAIN.equals(stage)) {
    out.add({"BAIL", BAIL});       // 主干
    out.add({"ARREST", CLOSED});
    out.add({"RELEASE", CLOSED});
} else if (STAGE_BAIL.equals(stage)) {
    out.add({"CLOSE", CLOSED});
}
```

设计要点：

- **刑事初查唯一出口是「刑拘」** —— 不再提供「直接取保」「直接释放」，否则强制措施与承办组别会与实际脱节。
- **行政只有一条线**：初查 → 批准行政处罚 → 已终结。
- **流转必须显式选分支**（刑拘/取保/释放后果完全不同），且**由领导确认**（`AuthContext.isFullAccess()`）。
- **流转自动同步强制措施**（转取保/监居 → `case_measure=BAIL`；转刑拘 → `DETENTION`），保证期限引擎对得上。

> 扩展方式：加阶段/改路径**只改 `CaseFlowTemplate` 一个类**，不动引擎与前端。

## 第 5 章 核心设计二：刑事 / 行政双类型体系

两类案件在**盯办方式**与**期限规则**上完全不同，系统为此做了分叉。

### 5.1 盯办三模块与措施映射

刑事盯办按**子模块**分三个页签，映射逻辑收敛在 `PoliceGroup.moduleOfMeasure`：

| 强制措施 | 归入模块 | 理由 |
|---|---|---|
| NONE / 空 / 拘传(SUMMONS) | `INITIAL` 初查 | 拘传只是到案手段，不改变「是否在押」 |
| 拘留(DETENTION) / 逮捕(ARREST) | `DETENTION` 刑拘在办 | 羁押类，阶段任务相同 |
| 取保(BAIL) / 监视居住(RESIDENCE) | `BAIL_RESIDENCE` 取保及监居 | 非羁押执行类 |

**维护约定**：新增措施先登记进 `PoliceGroup.MEASURES`，`moduleOfMeasure` 与 `measuresOfModule` 自动带上它——列表过滤、看板分桶、承办负荷都读这两个方法，不会出现「新措施哪张卡片都不算」的漏案。

### 5.2 行政盯办：只看期限节点

行政案件**没有强制措施页签**，盯办页面核心是「具体时限提醒」——逐条列出第 3/10/20 天内部监督节点。

### 5.3 状态列的口径（2026-10-14 定型）

| 页签 | 状态口径 |
|---|---|
| 初查 | **四态**：未分配 → 已分配 → 已签收 → 已反馈（由后端判定，前端只映射标签） |
| 刑拘在办 / 取保及监居 | **三态**：未开始 → 进行中 → 已完结（= 当前阶段待办完成情况） |

> 口径**只由后端算一次**，前端 `INVEST_STAGE_META` / `PROGRESS_STAGE_META` 只做标签与颜色映射，避免两处判定打架。

## 第 6 章 核心设计三：办理时限引擎（两套时钟）

`CaseDeadlineService` 是除阶段流程外最复杂的业务模块。

### 6.1 通用起算口径

> **起算当日 = 第 1 天。第 N 天 = 起算日 + (N−1) 天。**

```java
private static LocalDateTime day(LocalDateTime base, int ordinal) {
    return base.plusDays(ordinal - 1L);
}
```

到期时间归到当天 23:59:59；提醒从当天 00:00 生效。

### 6.2 刑事 · 拘留：按羁押期限三档分流

以**刑拘日期**（`measure_date`）起算，按 `detention_term` 分 3 / 7 / 30 天三档：

| 档位 | 生成的节点 |
|---|---|
| **3 天** | 第 3 天变更羁押期限（改 7 天/30 天/停止计算） |
| **7 天** | 第 4 天提醒移交 → 第 5 天移交预审 → 第 6 天移交法制 → 第 7 天届满 |
| **30 天** | 第 12 天提醒移交 → 第 15 天移交预审 → 第 19 天跟进审核 → 第 20 天移交法制 → 第 30 天届满 |

**7/30 天案**另有「预审/法制审核通过并接收」节点（须管理层据回执登记）。

**变更羁押期限**（`changeTerm`）：7 天 / 30 天 / PAUSE（停止计算，如精神病鉴定）/ RESUME（恢复）。暂停期间所有时限不提醒；恢复时把暂停时长累加进 `pausedSeconds`，基准日随之后移。

### 6.3 刑事 · 取保候审 / 监视居住

- **取保**：3 个月移交预审、半年移交法制/评估解除、1 年期限届满、每 3 个月传讯。
- **监居**：6 个月届满、每月传讯、距上次传讯不超过 3 个月。

### 6.4 行政：以「受案时间」为基准

```java
if ("ADMINISTRATIVE".equals(c.getCaseType()) && c.getAcceptTime() != null) {
    add(items, "ADMIN_CHECK_3",  "第3天所内部监督",  day(base, 3),  day(base, 3),  s.getAdminCheck3At(),  now);
    add(items, "ADMIN_CHECK_10", "第10天所内部监督", day(base, 10), day(base, 10), s.getAdminCheck10At(), now);
    add(items, "ADMIN_CHECK_20", "第20天所内部监督", day(base, 20), day(base, 20), s.getAdminCheck20At(), now);
    add(items, "ADMIN_30",       "第30天办结；未办结则呈延长文书", day(base, 30), day(base, 29), s.getAdmin30DocAt(), now);
    if (s.getAdmin30DocAt() != null)      // 呈了延长文书 → 出现「确认延长30天」
        add(items, "ADMIN_EXTEND", "确认延长30天（总期限60天）", day(base, 30), s.getAdmin30DocAt(), s.getAdminExtendedAt(), now);
    if (s.getAdminExtendedAt() != null)   // 确认延长 → 才出现第60天节点
        add(items, "ADMIN_60", "已延长30天：第60天前呈延长文书", day(base, 60), day(base, 59), s.getAdmin60DocAt(), now);
}
```

**关键点**：

- **行政必须登记 `accept_time`（受案时间），否则整套行政时限不生成。**
- 第 30 天、延长、第 60 天是**条件级联**的：只有呈了延长文书才出现「确认延长」，只有确认延长才出现第 60 天节点。

### 6.5 登记权限分级

| 操作 | 权限 |
|---|---|
| 登记办理时间（内部监督等） | 本案承办人 |
| 「审核通过并接收」 | 仅管理层（须据回执） |
| 「确认延长办案期限」 | 仅管理层 |
| 「变更羁押期限」 | 仅管理层 |

引擎里以 `AuthContext.isFullAccess()` + 承办人校验（`checkHandlerOrManager`）双重把关。

### 6.6 暂停/终止的提醒抑制

```java
if ("DONE".equals(status) || "CANCELLED".equals(status))
    for (Item item : items) { item.setReminding(false); item.setOverdue(false); }
if (paused)
    for (Item item : items) { item.setReminding(false); item.setOverdue(false); }
```

已办结/已撤销、或处于暂停计算的案件，**所有节点不再提醒也不再标逾期**。

## 第 7 章 核心设计四：追溯与撤回（双快照机制）

### 7.1 双快照

每次写操作前后各存一份完整案件快照（`CaseSnapshot`）：

```java
public class CaseSnapshot {
    private Boolean exists;                       // false = 该案件当时不存在
    private CaseInfo info;
    private List<CaseAssignee> assignees;
    private List<CaseFile> files;
    private List<CaseSuspect> suspects;
    private List<CaseTimeNode> timeNodes;         // 重要时间节点（2026-10-13 纳入）
    private List<CasePlan> plans;
    private List<CaseTodo> todos;
    private List<CaseLeaderOpinion> opinions;     // 领导意见（2026-10-13 纳入）
}
```

**撤回 = 把 before 快照原样写回。**

`exists=false` 的妙用：新建操作的 before、删除操作的 after 都是这种形态，回写即等价于删除 —— 于是**撤回逻辑统一成一句「写回 before」**。

### 7.2 为什么 opinions 必须一起快照

> 待办现在是**意见派生**的（`case_todo.opinion_id`）。若只快照 todos 不快照 opinions，撤回建案会删掉 todo 却把 opinion 留成孤儿 —— 而 `StaffTodoService.backfillFromOpinions()` 可能把孤儿意见**重新派生出待办**，表现为「案件已经撤了，待办却又冒出来」。

### 7.3 撤回本身也留痕

撤回是**一次新的写操作**，同样记日志。对一次「撤回」再撤一次 = **重做**。因此撤回可以反复做，形成可逆历史。

## 第 8 章 核心设计五：待办 = 意见的唯一载体

### 8.1 链路

```
领导提意见 → 系统派生待办 → 承办人看到待办 → 办理后提交反馈 → 领导勾选「已完成」
```

`case_todo.opinion_id` 记录派生来源，**保证「意见 → 待办」永远对得上**。

### 8.2 三处入口、同一链路

待办可从**建案时 / 指派时 / 案件详情**三处录入，但底层**同一条「意见 → 派生待办」链路**（批量录入走 `TodoBatchEditor.vue`）。这避免了「三处各写一套」导致的口径漂移。

### 8.3 两级子任务

`case_todo.parent_id` 支持两级。**权限边界**：主任务 = 管理层，子任务 = 承办人。

### 8.4 完成的两条硬规则

1. **勾选完成只允许领导与管理员**（2026-10-13）—— 民警提交反馈 ≠ 完成，必须领导勾选才闭环。防止「自己说办完了」。
2. **勾选子任务必须弹完整汇报弹窗** —— 不能列表直接勾掉，必须填完整汇报内容。

> 注意权限拦截点：`@FullAccessOnly` 是**方法级**的，由 `PermissionInterceptor` 在**进入方法前**拦截 —— 放到 Service 分层里拦是无效的。

## 第 9 章 权限骨架：角色、层级、办案组别

### 9.1 角色与全权限

| 角色 | 常量 | 全权限 |
|---|---|---|
| 局长 | BOSS | ✅ |
| 所长/大队长 | CHIEF | ✅ |
| 副职 | DEPUTY_CHIEF | ✅ |
| 法制员 | LAW_OFFICER | ✅ |
| 民警 | STAFF | ❌（受限） |

前端权限 getter 名为 **`isFullAccess`**（注意不是 `isAdmin`）。

### 9.2 组织层级由职务推导（`OrgRank`）

固定四层：**总 → 副总 → 组长 → 员工**。

> **为什么按职务定层**：以前组织树完全靠 `parent_id` 决定形状，结果「副总」和「总」平级、「组员」自己成了顶层（整棵树像三棵并排的树）。层级是**组织身份**，改由职务推导，`parent_id` 只决定「同层里挂到谁名下」。

判定顺序有讲究：**先「副」再「组长」，「长」最后兜底** —— 否则「副组长」会被误判成副总层、「组长」会被当成总。空职务按员工层处理。

> 前端 `utils/org.js` 是同一套口径的镜像，**改规则必须两边一起改**。

### 9.3 办案组别（`PoliceGroup`）

| 组别 | 常量 | 可接案件 |
|---|---|---|
| 初查组 | INITIAL | 初查任务 |
| 清案组 | CLEAR | 刑拘在办 |
| 不限 | NONE | **任何案件**（机动力量） |

**规则（2026-10-07 修订）**：

- 案件要求「初查组/清案组」→ 本组成员可接，**「不限」组成员也可接**（不限 > 其他任何组）。
- 唯一仍拦的：**初查组 × 清案组互换** —— 两个专业分工不互派。
- **取保及监居不限制组别**：清案组为主刑后清案设的，取保阶段既不是初查也不是清案，限制会让案件无处可派。
- 空值/非法值一律归一为「不限」（`normalize`）—— 存量员工没填组别不能因此派不出去。

> **权威来源是 `org_employee.police_group`（员工档案），不是账号**。账号上的组别只是注册自报值，有些账号（如 boss）根本没有员工档案。指派时前端会自动按所需组别过滤可选人员。

### 9.4 账号硬规则

- `audit_status` 非 1 **不能登录**（须审核）。
- 手机号**全局唯一**。
- 停用/删除/重置密码必须 `removeAll`（**强制清除该用户登录态**）。

## 第 10 章 实时机制：SSE 全量埋点汇聚

### 10.1 架构

`LogService.log` 是全量埋点**唯一汇聚点** → `SseHub.broadcast` → 前端 `store/events.js`。

`SseHub` 用 `CopyOnWriteArrayList` 存所有在线连接，`SseEmitter(0L)`（0 = 服务端不主动超时，断线由前端 `EventSource` 自动重连）。单条发送失败即摘除该连接。

### 10.2 前端消费

前端订阅 `case-event`，用于「办理进度实时刷新」「工作台最近操作自动更新」等全局联动。

> **改埋点只动 `LogService` 一处** —— 这是本系统对外承诺的一致性保证。

## 第 11 章 数据兼容与演进策略

### 11.1 加字段的统一走法

新增字段统一走 `bootstrap/SchemaMigration.NEW_COLUMNS`，**`schema.sql` 有双副本必须同步**：

- `app/backend/src/main/resources/sql/schema.sql`
- `app/sql/schema.sql`

二级索引只能放 `sql/index-mysql.sql`。

> 例：`case_deadline_state` 的行政/传讯节点字段（`admin_check_3_at`、`paused_seconds`、`pretrial_received_at` 等）就是通过 `NEW_COLUMNS` 补齐的。

### 11.2 存量数据归位口径

| 场景 | 处理 |
|---|---|
| `flow_stage` 为 NULL | 按 INITIAL 处理 |
| 强制措施为空 | 按 INITIAL（初查）模块 |
| `police_group` 为空/非法 | 归一为「不限」 |
| 组别下拉 | 一律选已有部门，部门异常标橙 |

### 11.3 列表页进度别用 N+1

`CaseVO` 已带 `flowStage` / `flowStageName` / `planDone` / `planTotal`，随列表一次返回。单案进度轮询才走 `flow/progress` 端点。

## 第 13 章 工程约定与踩坑清单

### 13.1 编码硬约定

- **Spring Boot 2.7 + JDK8**：新建后端文件用 `javax.annotation.Resource`（**非 jakarta**）；JDK8 无 `List.of()`，用 `new ArrayList<>()`。
- **权限注解**：`@FullAccessOnly` 为**方法级**拦截，放 Service 分层无效。
- **跨组件计数/状态必须放 Pinia store**；刷新计数走后端重数，**别本地 `-1`**（会与实际漂移）。
- **公安配色**：警蓝 `#1b4a8c` / 深藏蓝 `#12294a` / 警徽金 `#c8a45c`；布局基准全在 `styles/index.css`，页内别另写。
- **全项目禁悬浮提示** —— `el-tooltip` 归零、原生 `title` 清零，说明改**常驻内联文字**。

### 13.2 已修的坑（勿重犯）

| 坑 | 现象 | 修法 |
|---|---|---|
| MyBatis-Plus `apply()` 拼排序 | H2 语法错 | 排序用 `.last("ORDER BY …")`，不要用 `apply()` |
| `EChart.vue` 未注册图表类型 | 图表**静默不渲染、零报错** | 新图表类型必须先在 `EChart.vue` 注册 |
| 进度口径与流程面板不一致 | 列表进度虚高、两处数字对不上 | 统一「`stage` NULL 视为 INITIAL」同一套口径 |
| 勾选子任务直接勾掉 | 无汇报内容 | 强制弹完整汇报弹窗 |
| 侧栏红点 vs 任务页条数不一致 | 侧栏 3 条 / 页面 6 条 | 红点改 `pendingCount`（未完成总数），列表默认 PENDING |

### 13.3 开发/部署注意

- **开发库 H2 同时只能一个后端进程**（报 `Could not open .mv.db` 即重复启动）。
- **虚拟环境 `app/.venv`（Python 3.10.11）**，PyCharm SDK 显示版本不影响运行。
- **打包**：前端 `base='/api/'`，pom 拷 `dist` 进 `static`，必须 `clean package` 且先杀 8080。
- **内网放行 8080** 用 `scripts/open_lan_firewall.py`；本机自查通**不能作证**「别人能打开」。
