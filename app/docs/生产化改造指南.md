# CaseFlow 生产化改造指南

> 面向「案件指派系统」从本地演示版走向真正投入生产使用所需的改造清单。
> 每一条都对应代码里的具体位置，并标注**优先级**与**不做会怎样**。
>
> 版本：v1.0　适用代码基线：Spring Boot 2.7.18 + MyBatis-Plus 3.5.5 + Vue3

---

## 0. 当前状态与生产要求的差距（一张表看清）

| 维度 | 现在（本地演示版） | 生产要求 | 优先级 |
|---|---|---|---|
| 数据库 | 已切本地 MySQL 8（免安装实例）或 H2 文件库 | 独立 MySQL 8 主从 + 定期备份 + 迁移版本管理 | P0 |
| 数据库账号 | `caseflow/caseflow`、`root/root` 写在配置默认值里 | 全部走环境变量/密钥管理，禁用默认值 | P0 |
| 密码存储 | **明文**（`sys_user.password` 直接存，登录用 `equals` 比较） | BCrypt 加盐哈希 | P0 |

| 权限 | 只要登录就能看/改全部案件 | 按角色 + 按组织范围的数据权限 | P0 |

| 可观测 | 无 Actuator、无健康检查、无 traceId | Actuator + 结构化日志 + 监控告警 | P1 |

| 部署 | 本机 `dev.py` 起两个进程 | Nginx 托管前端 + 后端多实例 + HTTPS | P1 |

| 容量 | 表无归档策略 | 操作日志分区/归档 | P2 |

## 1. P0：上线前必须改完

### 1.1 数据库：从「能跑」到「能扛」

**已经做完的部分**（本次改造）：
- 本地 MySQL 8 免安装实例，数据落在 `.tools/mysql-data`，端口 3306，只监听 127.0.0.1
- 应用使用专用账号 `caseflow`，只授予 `case_flow.*` 权限，不用 root 连库
- 建表 + `sql/index-mysql.sql` 里 10 条索引已建齐
- `application-mysql.yml` 的 `continue-on-error` 已从 `true` 改为 `false`：MySQL 上建表若有方言问题会直接启动失败，不再静默带病运行

**生产还需要做的**：

1. **引入迁移工具**。现在靠 `schema.sql` + `IF NOT EXISTS`，只能加表、不能改列。改用 Flyway：
   ```
   V1__init.sql            -- 现有 schema.sql 内容
   V2__add_index.sql       -- index-mysql.sql 内容
   V3__xxx.sql             -- 以后每次改表一条
   ```
   配 `spring.flyway.baseline-on-migrate=true`，`spring.sql.init.mode=never`。

2. **删掉配置里的默认密码**。`application-mysql.yml` 现在是 `${MYSQL_PASSWORD:caseflow}`——那个 `:caseflow` 默认值上线必须去掉，改成 `${MYSQL_PASSWORD}`，密码通过环境变量或配置中心注入。

3. **字符集与时区显式声明**。JDBC URL 已带 `characterEncoding=utf8mb4&serverTimezone=Asia/Shanghai`，但库、表、列三级的字符集建议在迁移脚本里显式写 `utf8mb4 / utf8mb4_0900_ai_ci`，不要依赖实例默认。

4. **连接池按实例数算**。`maximum-pool-size: 10` 是单实例假设。若部署 4 个实例，总连接 40，要确认 MySQL `max_connections` 留够余量；高并发场景建议再加 `minimum-idle` 调优和慢 SQL 监控。

5. **`operation_log` 会最快膨胀**。它是全量埋点，写入量随操作线性增长。生产上：
   - `created_at` 加索引，按季度分区或定期归档到冷表；
   - 写入改为异步（`@Async` + 队列），不要让它拖慢主业务事务。

### 1.2 认证与鉴权（当前最大的风险点）

**问题 1：密码是明文。**
`AuthService.login()` 第 46 行：

```java
if (!user.getPassword().equals(req.getPassword())) {
```

`schema.sql` 里自己也写了注释「演示版明文，生产需 BCrypt 加盐」。改成：

```java
if (!passwordEncoder.matches(req.getPassword(), user.getPassword())) {
```

引入 `spring-boot-starter-security`（只用它的 `BCryptPasswordEncoder`，或直接引 `spring-security-crypto` 这个轻量包），并写一条迁移脚本把存量明文密码批量转成哈希。

**问题 2：登录态在内存里。**
`TokenStore` 用 `ConcurrentHashMap` 存 session。后果有两个：
- 后端一重启，所有人被踢下线；
- 一旦部署多个实例（负载均衡），A 实例签发的令牌在 B 实例上不认识。

两条路：换成 **JWT**（无状态，最省事，但要处理吊销），或把 `TokenStore` 换成 **Redis 实现**（代码里已经挖好了接口，替换成本低）。生产推荐 JWT + Redis 黑名单。

**问题 3：没有权限控制。**
`LoginInterceptor` 只判断「登录了没有」，不判断「能干什么」。搜索代码可以看到 `CurrentUser.role` 字段存在但**从未被用于校验**。上线前至少要加：
- 接口级：`ASSIGN` / `CLOSE` / `IMPORT` 等关键操作限 `BOSS` / `MANAGER`；
- 数据级：员工只能看指派给自己的案件，组长能看本组，领导看全部。这一层建议在 `CaseService` 的查询条件里统一注入「可见范围」，而不是散落到各 Controller。

**问题 4：CORS 全开。**
`WebConfig.addCorsMappings` 里 `allowedOriginPatterns("*")` 配合 `allowCredentials(true)`，等于允许任意网站带着用户凭据调接口。生产必须收成具体域名白名单，且前端与后端最好同域（Nginx 反向代理），从根上消除跨域。

### 1.3 附件存储

`FileService` 把文件写到 `./data/uploads`（相对启动目录）。生产问题：

- 换机器/多实例就找不到了 → 换对象存储（腾讯云 COS / 阿里云 OSS / 自建 MinIO）。代码里 `FileService` 已经做了「DB 存 `storage_path`、磁盘存实体」的分离，把读写换成 SDK 调用即可，改动面很小。
- **路径穿越**：`root.resolve(f.getStoragePath()).normalize()` 这种写法，如果 `storage_path` 来自数据库被污染，理论上可以跳出 uploads 目录。加一道断言：`resolved.startsWith(root)`。
- **上传校验**：现在只按扩展名判类型。生产要加真实 MIME 嗅探、白名单（pdf/docx/xlsx）、单文件大小与总量配额、以及病毒扫描（对公安类业务尤其重要）。
- **下载鉴权**：`/api/files/{id}/download` 目前只要求登录。案件材料属于敏感数据，必须校验「该用户是否有权看这个案件」，并记录下载行为到 `operation_log`。

### 1.4 操作撤回（Ctrl+Z）的生产化约束

撤回已经落地（`CaseSnapshotService` + `OperationLogService.undo`），实现是「写操作前后各存一份完整快照，撤回即把 `snapshot_before` 原样写回」。演示版够用，但生产要补三件事：

- **权限**：现在任何登录用户都能撤回任何一条案件操作。生产要限定为「本人操作 + 一定时间窗（如 10 分钟内）」或「管理员可撤任意一条」，并做成可配置策略；撤回动作本身必须进不可篡改的审计日志（现有 `operation_log` 可写，但要保证应用账号没有 `DELETE/UPDATE` 权限）。
- **并发**：现在的安全规则是「只能撤回该案件上最新的一条」，但**没有乐观锁**——两个管理员同时撤回、或一人撤回的同时另一人在改同一案件，仍可能互相覆盖。做法：`case_info` 加 `version` 列，撤回时 `UPDATE ... WHERE id=? AND version=?`，影响行数为 0 就提示「数据已变化，请刷新」。
- **快照的体积与留存**：快照是整份对象的 JSON，写频率高、增长快。生产建议：① 只对**有业务意义的字段**存快照（现在是整行 + 全部指派关系 + 附件列表）；② 给快照加保留期（如 90 天），过期后把 `snapshot_before/after` 置空但保留 `content` 文本；③ `operation_log` 按 `created_at` 分区或定期归档到冷表（`sql/index-mysql.sql` 已有 `idx_log_target` 支撑按对象查询）。

## 2. P1：让系统真正能运维

### 2.1 可观测性

- 加 `spring-boot-starter-actuator`，暴露 `/actuator/health`（给负载均衡做健康检查）与 `/actuator/metrics`（对接 Prometheus）。注意 `context-path` 是 `/api`，健康检查地址会是 `/api/actuator/health`。
- 日志改成结构化输出（JSON），并在 `LoginInterceptor` 里生成 `traceId` 放进 MDC，这样一次请求的「登录 → 查案件 → 改状态」三行日志能串起来。拦截器已经有 `afterCompletion` 钩子，`MDC.clear()` 放这里即可。
- Spring Boot 2.7 用的是 Spring MVC + 线程池，`MDC` 在异步场景要注意传递。

### 2.2 到期提醒要主动推送

现在「到期提醒」是**打开页面时才计算**——没人开页面就没人知道有案子逾期，这不符合「盯到期」的业务初衷。生产要做成：

- `@Scheduled` 每天固定时间（如 08:00）扫一遍 `case_info.deadline`，把「今日到期 / 3 日内到期 / 已逾期」三类生成提醒任务；
- 推给主办 + 其上级（`org_employee.parent_id` 链路现成可用）；
- 渠道：站内信 → 企业微信/钉钉机器人 → 短信。建议先做前两级。
- 多实例部署时定时任务会重复执行，需加分布式锁（Redis）或改用调度中心（XXL-Job）。

### 2.3 测试

目前**一个测试都没有**。至少补三类：

1. 服务层单测：`CaseService.assign()` 的改派留痕、`deadline` 置空、状态机流转（`PENDING_ASSIGN → ASSIGNED → IN_PROGRESS → DONE`，禁止从 `DONE` 回到 `IN_PROGRESS`）；
2. Mapper 集成测试：用 H2 或 Testcontainers 跑真 SQL，覆盖 `id_path` 子树查询、`StatsService` 的 9 组统计口径；
3. 接口测试：登录 → 建案 → 指派 → 办结 全链路。

「统计口径对不对」这类问题，靠人眼看页面很容易漏，必须落到测试里。

### 2.4 部署形态

```
用户浏览器
   │ HTTPS
   ▼
Nginx ──┬── /            → frontend/dist 静态文件（gzip、缓存策略）
        └── /api/        → 后端实例组（8080/8081...）
                             └── MySQL（主从）
                             └── Redis（会话/缓存/分布式锁）
                             └── 对象存储（附件）
```

- 前端 `npm run build` 出 `dist`，交给 Nginx。注意现在 `vite.config.js` 只有 dev 的 `proxy`，生产要么同域部署（推荐，`baseURL` 用默认 `/api`），要么设 `VITE_API_BASE` 指向后端域名。
- 上线前把 `server.servlet.context-path: /api` 与 Nginx 的 location 对齐，避免 404 排查半天。
- 后端打成一个可执行 jar（`mvn package`），用 systemd / NSSM / Kubernetes 托管，**不要**再用 `spring-boot:run`。

### 2.5 备份容灾

- 每日全量：`mysqldump --single-transaction --routines --triggers case_flow`，压缩后传异地；
- 开启 binlog，保留 7-30 天，支持按时间点恢复（PITR）；
- **恢复演练**：备份没验证过等于没备份。每季度在测试环境恢复一次，确认能跑起来；
- 附件与数据库要一起备份，否则恢复出来的案件指向一堆不存在的文件。

## 3. P2：工程化与体验

| 项 | 做法 |
|---|---|
| 接口文档 | 加 `springdoc-openapi-ui`，注解化后自动出 Swagger，前端联调不用再翻 Controller |
| 前端工程 | 目前 `Element Plus` 全量引入，生产建议按需引入 + 路由懒加载，首屏体积能降一半 |
| 缓存 | `StatsService` 的 9 组统计每次全表扫，可加 30-60 秒缓存；字典数据（`DictHolder`）改成启动加载 + 手动刷新 |
| 数据归档 | `case_info` 按年分表或至少按「办结时间」建归档策略，避免三年后单表千万行 |
| CI/CD | 提交触发：前端 lint+build、后端 `mvn verify`、构建镜像、推测试环境。每次手工部署迟早出错 |
| 操作留痕 | `operation_log` 已全量埋点，建议再加「操作前后值」字段（现在 `content` 是拼好的可读串，不够审计用） |
| 案例编号 | `case_no` 形如 `CA-20260928-001`，高并发下生成逻辑要加锁或改用独立序列表，否则会撞唯一键 |

## 4. 建议的推进节奏

**第 1 周（不做不能上线）**
密码 BCrypt、令牌外置（JWT/Redis）、CORS 白名单、附件下载鉴权、配置里去掉默认密码、Flyway 接管建表。

**第 1 个月（能稳定运维）**
数据权限（员工/组长/领导三档可见范围）、Actuator 健康检查 + 日志 traceId、Nginx + HTTPS 部署、每日备份、到期提醒定时任务。

**第 3 个月（可持续演进）**
测试覆盖核心链路、对象存储迁移附件、统计缓存、接口文档、CI/CD、操作日志归档。

## 5. 一句话总结

**这个系统当前的瓶颈不在功能，而在「单机假设」** —— 数据存本地文件库、会话存进程内存、附件存本机磁盘，这三件事决定了它现在只能跑在一台机器上、且重启就丢状态。
把这三样换掉（MySQL + Redis/JWT + 对象存储），再加上密码哈希和权限校验，它就从「能演示」变成了「能上线」；剩下的全是运维层面的补课。
