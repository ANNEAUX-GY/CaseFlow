### ★ 核心事件：jar 内建表脚本缺 5 张表 ★
**现象**：用补丁包里的 jar 启动（全新库），日志出现
`[SchemaMigration] 增量建列失败，撤回功能可能不可用：Table "case_question" not found`。

**根因（关键，容易再犯）**：
- `app/backend/src/main/resources/sql/schema.sql` 是早期手工拷贝的副本（**16 表**），
  权威版本 `app/sql/schema.sql` 已是 **21 表**。
- pom 虽然把 `../sql` 映射进 `classpath:/sql/`，但 **maven-resources-plugin 默认
  `overwrite=false`** —— 同名文件**先写入者胜**，`src/main/resources` 先处理，
  于是**陈旧副本顶掉了正确版本**。
- 缺的表：`case_question` / `case_close_request` / `case_deadline_state` /
  `case_time_node` / `todo_preset`。
- 后果：程序自建表建不全 → SchemaMigration 补列时遇表不存在**整体抛异常** →
  其后 60+ 列 + 类别字典种子 + 时限迁移**全部跳过**（静默半残）。

**修复**：
1. 删掉 `src/main/resources/sql/schema.sql`（含空目录）。
2. pom 的 `src/main/resources` 资源**显式 exclude** `sql/schema.sql` 与
   `sql/index-mysql.sql` —— 建表脚本一律以 `app/sql/` 为唯一数据源。
3. `SchemaMigration.ensureColumns` 改**逐列容错**：单列失败只记录、不中断，
   末尾汇总一条 WARN。原来一遇错就整体抛出，把后续所有步骤一起带走。
4. `app/sql/schema.sql` 补 `case_file.todo_id` 与 `org_employee.origin`
   （此前只登记在 NEW_COLUMNS，靠启动兜底；现已对齐，脚本比对无差异）。

**实跑验证（4 项全过）**：
- 升级演练：旧 jar 建的 16 表库 → 新 jar 启动 → 零 ERROR，补 14 列 + 种 13 条小类。
- 全新库：零补列零 ERROR（证明建表脚本已完整）。
- 缺表容错：`--spring.sql.init.mode=never` 空库启动 → 79 列汇总为一条 WARN，不中断。
- 便携包解压 + 包内自带 Java 启动 → 3 秒 HTTP 200，boss 登录成功。
- 三个包内 jar 的 SHA256 与构建产物完全一致。
