## 案件关键节点「点对点通知」方案设计（仅出方案与文档，未写代码）

用户诉求：给一个思路——如何让处于关键节点的案件点对点通知到主办和经办人的手机，通知内容含案件编号/名称/进度/期限等。

产出：`docs/关键节点通知方案.md`（十节，含数据模型 SQL、企微接口示例、分级矩阵、分期节奏、上线前外部事项）。回复里配了 3 张图（通知链路架构 / 通知升级阶梯 / 手机端文案样式）。

### 方案里的关键判断（后续若实施，务必守住）

1. **关键节点只分两类**：动作型（指派·改派、期限变更、办结·撤销、撤回、待指派超时、久拖未动）用事件驱动；时间型（临期 T-3/T-1、当天到期、逾期、严重逾期）用定时扫描。**不要每个操作都推**，否则两周内大家就关掉通知。
2. **事件源不用新造**：`operation_log` 已全量埋了 `CREATE/UPDATE/ASSIGN/STATUS/DELETE/UNDO` 且带快照，通知直接复用，在 `logService.log(...)` 之后投递事件即可。
3. **收件人必须从 `case_assignee`(ACTIVE) → `org_employee.phone` 反查，不能走 `sys_user`**——一线办案人多数没有系统账号，但都在员工图谱里且有手机号。主办必收全量、协办收精简、上级**只在出事时**（逾期/超时/久拖）才叫醒。
4. **绝不能同步发消息**：事务内只 INSERT `notify_task`，由 `@Scheduled` 投递进程异步发（Outbox）。同步调企微会拖慢甚至回滚案件操作。
5. **必须做「取消未发出的通知」**：办结/撤销/改派时把该案（或原承办人）`PENDING/RETRY` 的任务置 `CANCELLED`。办结后还收到催办短信，对信任伤害最大，且极易漏。
6. **幂等键** `caseId:nodeCode:receiverId:channel:cycle`（时间型 cycle=YYYYMMDD，动作型=事件时间戳）+ UNIQUE 索引，天然防重复。
7. **群机器人 webhook 不是点对点**（发到群、无法指定个人），必须用企微**自建应用** + `touser={userid}` + `textcard`。项目里 `org_employee.employee_no` 建议直接对齐企微 userid，避免维护两套 ID。
8. **短信正文不放敏感案情细节**，只放编号 + 名称简称 + 期限，详情引导到系统内看（登录后可见=天然权限控制）；`【案件指派】` 同时充当签名与模板标识，报备后不可随意改。
9. **聚合防风暴**：同一人 10 分钟内同类通知 ≥3 条合并成摘要。批量导入、一次性指派多协办、每日扫描三个场景最易触发。
10. **静默时段** 21:00–08:00 不发非逾期类短信/语音，逾期类不受限但同案每日最多 1 条。

### 待确认的外部事项（会直接卡进度）

- 企微：管理员建自建应用拿 corpid/secret/agentid，服务器公网 IP 进可信 IP 白名单。
- 短信：签名 + 模板报备（1–3 工作日），含「案件/诈骗」等词有额外审核。
- 语音外呼：需语音网关资质 + TTS 模板报备。
- 若单位已有 OA/短信平台，**优先对接现有平台**，省掉自建通道。

### 新增表（登记时记得走 SchemaMigration）

`notify_channel`（员工渠道绑定：employee_id/channel/address/verified/status）、`notify_task`（待发任务 + 投递留痕合一：biz_key 唯一、status/retry_count/next_retry_at/provider_msg_id/sent_at/delivered_at）。`@Scheduled` 需新增 `@EnableScheduling`，项目此前无任何定时任务。

## 内网共享部署方案（物理隔离 · 10–50 人）

用户诉求：「给我提供思路，如何用单位内网进行共享使用这个系统」。经 AskUserQuestion 确认：**完全物理隔离**、**10–50 人**、服务器系统待定（让我建议）。

产出：`docs/内网共享部署方案.md`（九节，含拓扑图、三道摆渡清单、逐步实施、Nginx 配置、验收清单）。

### 核实到的关键事实（部署方案的事实基础，改动代码时别踩）

1. `server.servlet.context-path: /api`，前端 axios `baseURL = '/api'` → **天然同源，不需要跨域**。
2. 前端是 **hash 路由**（`#/dashboard`）→ 静态托管**不需要 try_files fallback**，永远不会"刷新 404"。
3. **`LoginInterceptor` 拦 `/**`，只放行 `/auth/**`、`/h2-console/**`、`/console/**`、`/error`**。若改成"fat jar 内嵌前端"的部署方式，`index.html` 与 `/assets/*.js` 会被 401 拦掉 → **打开即白屏**。这是部署当天最容易卡住的点。
4. 后端**目前没有**托管前端的配置（只配了 h2-console）。
5. 上传目录是相对路径 `./data/uploads` → 生产必须用 `--caseflow.upload-dir=` 覆盖成绝对路径。
6. `finalName: case-flow-backend`；`mvn package -DskipTests` 产出 `backend/target/case-flow-backend.jar`。
7. **已实测前端 `vite build` 通过**：12 秒，2243 模块，产物 index-*.js 1.06MB（gzip 350KB）、总 dist 约 2.5MB。
8. `AuthController` **只有 login/logout/info/dict 四个接口，没有任何账号管理功能**，系统里只有 `boss/admin123` 一个演示账号。`sys_user.employee_id` 字段已预留与员工图谱的关联（设计时就想到了，只差功能）。
9. 安全待收项：密码明文、token 支持 `?token=` URL 参数传入、CORS `allowedOriginPatterns("*")` + allowCredentials、dev 下 h2-console 开启。

### 方案核心判断

- **形态：Nginx + 独立 jar**（不是"一个 jar 全包"）。理由：URL 不带端口对 45–50 岁用户友好；静态文件不经过 Spring，**顺带绕过第 3 条的 401 白屏坑**。若选一 jar 全包，只能挂 `http://ip:8080/api/`。
- **系统：优先向 IT 要 Windows Server 虚拟机**。理由：项目资产（`mysql_local.py` 免安装 MySQL、`dev.py`、`.venv`）全是 Windows 原生的，零改造；免安装 MySQL 解压即用、不注册服务、不要管理员权限、卸载=删目录，契合内网"可回退、不动系统"。选 Linux 则 `mysql_local.py` 用不了，要换 tar.gz 安装 + 改写脚本。
- **隔离环境下服务器上「不需要」Node / Maven / Python**——只装 JDK + MySQL + Nginx。最忌讳"把整个开发环境搬进内网"。
- **建库改用纯 SQL**（文档里给了完整的 `CREATE DATABASE` + `CREATE USER` + `GRANT` 片段），服务器上没有 Python 也能初始化。
- **`client_max_body_size 100m` 必须加**：Nginx 默认 1MB，不加则上传案件材料必然 413（后端 `max-request-size` 是 100MB）。
- **后端 `--server.address=127.0.0.1` + MySQL 只监听本机**，Nginx 独占 80 对外，8080/3306 不对内网开放。
- Windows 上必须加 `-Dfile.encoding=UTF-8`，否则中文日志/文件名乱码；**Windows Update 要设手动**（半夜自动重启打补丁 = 第二天全单位打不开）。
- **上线前必须先补账号体系**：50 人共用 `boss` 账号 → 操作日志的操作人全是同一人 → **追溯和撤回功能直接失效**。最小集合：账号管理页（建/停用/重置密码）、`sys_user.employee_id` 关联员工图谱、首登强制改密、BCrypt。
- 规模真相：50 人单位实际同时在线通常 <10 人，**单实例足够，不要引负载均衡和集群**。
- 验收清单里两条极易漏：**服务器时间要同步 NTP**（时间不对则逾期判断全错）、**备份必须演练过一次恢复**。

### 坑（新增，务必记住）
1. **Lombok 在 JDK 25 下不生效**（`@Data` 不生成 getter/setter，报「找不到符号」）。编译/打包必须 `JAVA_HOME="C:/Program Files/Java/jdk1.8.0_172"`。
2. **`run_in_background` 起的任务在后端起来后会被回收** —— 单独起 MySQL 那条链路全挂。**必须把「启库 + 起服务」放在同一个常驻任务里**，进程树才不被回收。
3. **`curl` 会走本机代理环境变量**（实测 `127.0.0.1:54302`），本地自检一律加 `--noproxy '*'`，否则报 502 误判服务挂了。
4. **运行中的 jar 会锁住 `target/`**，`clean package` 失败。先 `taskkill` 掉 8080 再打包。
5. `puppeteer` 传路由参数时 MSYS 会把 `/cases` 转成 Windows 路径 → 脚本里 `export MSYS_NO_PATHCONV=1`。

### 附件存储（方案，未动代码）

- 关键设计：抽 `StorageService` 接口（put/get/delete/exists）+ Local/Nfs/S3 三实现，配置 `caseflow.storage.type` 切换；`storage_path` 语义升级为**相对 key**（不含盘符），换后端时数据库不用改。
- 明确反对：**不要把附件写进数据库 BLOB**。
- 高性价比补充：上传时存 SHA-256（去重 + 防篡改凭证）、删除改软删、下载也记 operation_log。

## 修 Bug：账号管理审批通过后侧栏红点不消失

用户反馈截图：「这个账号管理通过后红点没消除」——列表已是「没有待审核的注册申请」，侧栏「账号管理」仍挂红色角标 2。

### 根因
侧栏红点是 `layout/Layout.vue` 里的**局部 `ref` + 只在 `onMounted` 取一次**。Layout 是父级路由组件、**整个会话只挂载一次**，而审批动作发生在 `views/UserManage.vue`；两处各拿各的数，审批后 Layout 那份永远不重取。UserManage 自己的 `pendingCount` 因为 `load()` 里会刷新，所以列表空了、侧栏还挂着 2。

### 改法
- 新增 `frontend/src/store/pending.js`（Pinia）：`count` state + `refresh()`（走后端 `GET /users/pending-count` 重新计数，失败归零）+ `reset()`（退出登录清掉，防换人登录看到上一个人的红点）。
- `Layout.vue`：删掉局部 ref，改用 `computed(() => pendingStore.count)`；`onMounted` 取一次 + **`watch(() => route.path, loadPending)` 每次切页重取**（兜住审批后的刷新，也能看到别人从另一台电脑刚提交的申请）；`onLogout` 里 `pendingStore.reset()`。
- `UserManage.vue`：删掉局部 ref，改为同一 store 的 computed；`load()` 里 `await pendingStore.refresh()`。因为**所有变更操作（审批/驳回/启停/删除）都走 `load()`**，所以一改就全覆盖。
- 关键：刷新用**后端重新计数**而不是本地 `-1`，并发审批/驳回/停用场景下本地计数会算错。

### 验证
`badgecheck.mjs`（`C:/Users/adamin/.workbuddy/binaries/node/workspace`）：用 fetch 造 2 个待审核申请 → 浏览器注 token 进 `#/users` → 点「通过」→ 弹窗「确定」→ 全程**不刷新页面**读取 `.cf-aside .cf-nav-badge`。
实测 `2 → 1 → (无)`，后端 `pending-count` 同步归零。截图 `badge-1-初始.png` / `badge-2-审批一个后.png` / `badge-3-全部审批后.png`。
注意：puppeteer 里定位弹窗必须「可见（`offsetParent !== null`）+ 标题匹配」，页面有 4 个 `el-dialog`，`querySelector` 会选到隐藏的那个。

### 顺带
- 清理了自动化造的临时账号（`bdg*`），保留 boss / e2e_law / e2e_staff 与用户手动注册的「金所长」「见习警员郭奕」。
- 已把「`el-dialog` 多实例定位」补进 `local-page-screenshot-verify` 技能第 6 条。

## 三件事：收紧办结/撤销权限 · 手机号注册登录 · 修手机打不开 + 跨网方案

用户原话：「1、非管理层权限还是太大了，案件的办结和撤销非管理层无权操作；2、登陆账号可以选择用注册的手机号进行注册，不一定要用用户名；3、http://192.168.2.118:8080/api/ 用手机同一局域网打不开，要求可以局域网或者跨网使用，方案可以使用 tailscale 或者 cpolar，保证响应速度和数据更新速度」

### 1. 办结 / 撤销收紧为管理层专属
- 后端：`CaseService.MANAGER_ONLY_STATUS = {DONE, CANCELLED}`，`changeStatus` 里 `!AuthContext.isFullAccess()` 就抛 `BizException(403, …)`，文案与 `PermissionInterceptor` 保持一致。**普通民警仍允许 ASSIGNED→IN_PROGRESS**（「开始处理」是经办人自己的动作，不该挡）。
- 前端：`CaseDetailDrawer` 加 `canManage = computed(() => userStore.isFullAccess)`，隐藏「办结」「撤销」并补一行说明「办结 / 撤销为管理层权限」。
- **注意：`useUserStore` 的 getter 名是 `isFullAccess`（不是 `fullAccess`）**，写成 `userStore.fullAccess` 会是 undefined → 按钮静默消失（连管理层都看不到）。踩过一次。
- 顺带补上路由守卫：`meta.fullAccessOnly` 现在真的判断角色并重定向 `/dashboard`（之前只写了 meta、没实现，靠后端 403 兜底）。`store/user.js` 导出 `isFullAccessRole(role)` 供守卫使用（守卫里拿不到 Pinia 实例，只能读 localStorage）。

### 2. 手机号可作为账号注册与登录
- `support/Validators`（新）：`isPhone` 正则 `^1[3-9]\d{9}$`、`maskPhone` 脱敏、`trim`。
- 注册（`AuthService.register`）：**手机号必填 + 格式校验 + 唯一**；**登录名可留空，留空则用手机号当登录名**；留空以外仍需 ≥3 字符且唯一。
- 登录（`AuthService.login`）：`findByAccount()` 先按登录名匹配，匹配不到再按手机号匹配。**用 selectList 取首条而不是 selectOne**，避免历史数据重复导致 `TooManyResultsException`。
- `UserService.checkPhone(raw, excludeId)`：账号管理页建/改账号也走同一套手机号规则，改自己时排除自身 id。
- 前端：注册页手机号提到第一位（带必填星号），登录名移到姓名后面并标注「可留空，默认用手机号登录」；登录页占位符改「用户名 / 手机号」。

### 3. 手机打不开 = Windows 防火墙没放行 8080（根因）
- 诊断结论：网络类型 **WLAN → Public**；Domain/Private/Public 三个 profile 全部 Enabled；`netsh advfirewall firewall show rule name="CaseFlow 8080"` 返回「没有与指定标准相匹配的规则」→ **无入站放行**。
- **最容易误判的点：本机用 127.0.0.1 甚至用局域网 IP 访问都是通的（不过防火墙 / 自己发给自己），所以"本机能打开"完全不能证明服务对局域网开放。**
- 产物 `scripts/open_lan_firewall.bat`：**必须 GBK 编码 + CRLF**（`Path.write_text(..., encoding="gbk", newline="\r\n")`），否则 cmd.exe 按 ANSI 解码会乱码。脚本自带 `net session` 判权限 + `Start-Process -Verb RunAs` 自提权；只加一条 `profile=any` 的 TCP 8080 入站规则，不动其它设置；**不改网络类别为 Private**（那会降低公用 WiFi 下的安全性，`profile=any` 已够）。
- `scripts/start_lan.py`：新增 `lan_ips()`（默认路由地址排第一，其余标注为虚拟网卡可忽略）、`firewall_rule_exists()`（`netsh ... show rule` 只读查询，无需管理员）、`warn_firewall(port)`（明确写"症状：本机能打开，手机打不开"）、`show_qr(url)`。

### 4. 顺带修掉的会话问题（否则手机访问很别扭）
- `TokenStore` 原来是**单点登录**：`userToToken` 让同一账号第二次登录就把第一个 token 顶掉 → **手机上登录，电脑就掉线**。
- 改成多端在线：同一账号最多 5 个会话（超了按 `createdAt` 挤掉最早的），`remove(token)` 只销毁当前会话。
- 新增 `removeAll(userId)`：停用账号 / 删除账号 / **重置密码** 后立刻把该账号全部踢下线（拦截器只校验 token、不会回查 `sys_user.status`，只改状态位是踢不掉的）。

### 5. 跨网方案（`docs/跨网访问方案.md`）

### 4. 踩到的两个真坑（都靠实测才发现）

- **全屏弹窗被承办人选择表撑破**。`el-form-item__content` 是 flex 容器、它的直接子元素又是 flex 项，两层的 `min-width` 默认都是 `auto` = 不小于自身 min-content，而 `el-table` 的 min-content = 各列 `min-width` 之和（570px）→ 整行被顶成 642px，表现为「搜索框和表格右边被裁掉」。修法：`.el-form-item__content, .el-form-item__content > * { min-width: 0; max-width: 100% }`。**这类 flex 溢出的通用判据**：`scrollWidth - clientWidth > 0` 逐层往下找，就能定位到是哪一层的 min-content 顶住了。
